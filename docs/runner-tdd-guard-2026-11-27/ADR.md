## ADR-024 테스트 먼저가 아닌 step도 기존 테스트 파일 수정 · 삭제를 되돌린다

- 상태: 결정 (2026-11-28). T1 · T2 사용자(AI 추천 수용), T3 지휘 판정(AI 추천 수용, 사용자 반려 가능), T4 · T5 AI가 정함(지휘 판정, 사용자 반려 가능), T6~T8 지휘 판정(사용자 반려 가능, 새 맥락 리뷰 1회차). 열린 결정 0
- 맥락: 러너 판정 4(「RED 뒤 테스트 파일 무변경」)는 `tdd: true` step 안에서만 돈다(`skills/sdd-run/scripts/sdd_runner.py:624-639`). `tdd: false` step(측정 포함)에는 테스트 파일 검사가 없어 구현이 기존 테스트를 고치거나 지워도 통과한다. 사용자 원칙 「구현 세션은 테스트 케이스를 함부로 고치면 안 된다」와 부딪히는 자리가 여기 하나다(#86 검증 세션 확인). 한편 `skills/sdd-plan/SKILL.md:39`는 이동 리팩터의 이동 step을 「테스트 파일도 rename · package 줄이 바뀐다」는 이유로 일부러 `tdd: false`로 두고, 이 레포 지난 계획의 `tdd: false` step 76개 중 6개가 이름 바꾸기 · 삭제에 따라 기존 테스트 파일 수정을 계획했다(restructure-rename 1 · 2 · 3, restructure-gate-summary 3, restructure-trim 1, restructure-absorb 9의 step 파일)
- ADR 조건(`skills/sdd/references/design.md` 「끝」 3번): 되돌리기 비싸다(index.json step 칸을 계획 · 러너 · 문서가 같이 쓴다) · 코드만 보면 왜 계획 칸으로만 여는지 모른다 · 버린 방법이 있다

### T1 예외 범위

- 칸이 연 파일만 판정 4'(아래 T2)에서 뺀다. 판정은 이름 바꾸기 감지를 끄고(`--no-renames`) 보므로 이름 바꾸기는 「옛 경로 지움 + 새 경로 추가」다 — 옛 경로를 칸에 적으면 받는다(새 경로는 추가라 원래 받는다)
- 칸은 계획(`sdd-plan`)이 쓴다. 나눔 모드는 검증 세션이 쓰고 지휘가 step 계획을 확인한다 — 테스트 수정 허락을 계획 확인 한 자리에서 본다
- 버린 방법: A 예외 없음(이동 리팩터 · 이름 바꾸기 step마다 blocked → 검증 수정 → 재개로 한 번씩 멈춤, `sdd-plan:39` 패턴을 고쳐 써야 함) / C 내용이 같은 순수 이름 바꾸기만 자동 허용(지난 6건 대부분이 파일 안 경로 · 문구 수정이라 못 덮음)
- 대가: index.json step에 선택 칸 1개가 는다(status 값 4개 그대로, `phases_status.py --check` 안 건드림). 칸에 적으면 그 파일은 그 step에서 무엇이든 바뀔 수 있다 — 바뀐 내용이 이유와 맞는지는 리뷰 몫이다

### T2 되돌린 뒤

- 판정 4'(`tdd`가 아닌 step, 측정 포함): BASE ~ HEAD 순변화(`git -c core.quotePath=false diff --no-renames --name-only -z BASE HEAD` — git 기본값은 이름 바꾸기의 옛 경로를 숨기고 비ASCII 경로에 따옴표를 붙인다, 리뷰 1회차)에서 테스트 파일(`TEST_FILE`, `phases/` 밖)이고 BASE에 있었고(`cat-file -e BASE:<경로>`) T1 칸에 없는 경로를 BASE 내용으로 되돌린다(`git checkout BASE -- <경로>`, 지운 파일도 같은 명령으로 복원). BASE에 없던 경로(추가)는 남긴다
- 되돌렸으면 판정 4와 같은 꼴로 커밋(`test: step N — 테스트 수정 되돌림`)하고 실패를 낸다: 「테스트 파일을 고쳤다(되돌림): <경로 최대 5개> — 기존 테스트 파일은 계획 칸(test_edits)에 적힌 것만 고친다. 고쳐야 하면 blocked + 이유」. 재시도 수 · `last_error` · `attempts`는 지금 실패 경로 그대로다
- 재시도에서 되돌림 커밋은 BASE 뒤에 남지만 순변화가 0이라 다시 걸리지 않는다
- 버린 방법: B 되돌리고 판정 계속(되돌린 뒤 verify가 깨지면 「verify 실패」만 남아 원인이 가려진다)

### T3 시작 커밋

- `prompt --role impl`이 그 step에 `base`가 없으면 그 순간 HEAD를 `pin_base`로 고정한다. `--base`를 주면 지금처럼 그 값이 먼저다. tdd step은 검증의 `prompt --role test --base`가 이미 고정해 두므로 바뀌지 않는다
- 나눔 모드 blocked(red 없음)는 BASE를 지운다(`:960-961`). 검증이 그사이 테스트를 고쳐 커밋하고 pending으로 되돌리면 다음 구현 차례는 그 커밋 뒤를 BASE로 잡아 검증의 수정이 되돌려지지 않는다
- 버린 방법: B 구현 세션 지시문에 `--base`를 적게 하기(#80 트랙에서 빠뜨려 judge가 거절했고, 늦게 잡힌 BASE는 판정 4'가 테스트 변경을 하나도 못 본다)

### T4 칸의 꼴 (A)

- A `test_edits` 객체(경로 → 이유). glob을 두지 않는다 — 「적힌 파일」만 뜻하고, `tests/**` 한 줄이면 테스트 전부가 열린다. 이유가 칸 안에 있어 지시문 · 판정 메시지 · 리뷰가 같은 글자를 본다. `start`가 계획 실수(tdd step에 씀 · 이유 빈칸 · 테스트 파일이 아닌 경로)를 첫 step 전에 잡는다 — `kind: measure` + `tdd: true` 검사(`:460-463`)와 같은 자리
- 버린 방법: B 경로 배열 + 이유는 step 파일 본문: 러너가 이유 칸을 확인할 수 없다(「이유와 함께」가 글 규칙으로만 남는다)

### T5 blocked 보고 (A)

- 지금 `check`는 status가 blocked면 판정 없이 돌려준다(`:609-610`). 그 뒤 `record`가 남은 변경을 `wip:` 커밋으로 묶고 BASE를 지운다(`:958-966`). 그래서 구현이 테스트를 고친 채 blocked로 보고하면, 검증이 pending으로 되돌린 뒤 새 BASE가 그 `wip:` 커밋 뒤로 잡혀 수정이 판정 4' 밖으로 빠진다
- A blocked 기록 전에 판정 4'와 같은 되돌림을 돌리고 실패 대신 `blocked_reason` 끝에 「(테스트 수정 되돌림: <경로>)」를 붙인다. 고친 내용은 `wip:` 커밋과 되돌림 커밋으로 기록에 남아 검증이 재판정 때 볼 수 있다
- 버린 방법: B 그대로 두고 검증 재판정이 diff를 보게 한다(사람 · 검증이 놓치면 테스트 수정이 씻긴다)

### T6~T8 (새 맥락 리뷰 1회차, A)

- T6: 진행 중 index.json은 구현이 status를 쓰려고 원래 고치는 파일이라, 거기서 칸을 읽으면 구현이 자기 허가를 써 넣을 수 있다. BASE 커밋의 계획이 「계획에 미리 적은 파일」(T1)이다. 대가: 검증이 step 도중 칸을 더하면 계획을 고쳐 커밋한 뒤 다음 시도(새 BASE)부터 적용된다. 버린 방법: B 그대로(리뷰가 diff로 거름)
- T7: 보고 경로는 셋(완료 · blocked · 실패 멈춤)이다. T5가 blocked를 막았으니 실패 멈춤도 같은 꼴로 막는다. 버린 방법: B 그대로(사람이 재개 전에 diff를 봄)
- T8: T4 「glob 없음 · 시작 때 거름」의 연장. 글자 그대로 비교라 그대로 두면 안전한 쪽(되돌림)으로 실패하지만, 계획한 사람은 judge에서야 안다. 버린 방법: B 그대로

### 결과

- 1회 모드 · 헤드리스 `run`도 같은 `check`를 쓰므로 같이 걸린다. 이미 돌고 있는 계획 중 `tdd: false` step이 기존 테스트 파일을 고치는 것은 칸을 더하기 전까지 재시도 · 멈춤으로 간다
- 테스트 먼저 step(`tdd: true`)의 판정 4는 그대로다(설계서 결정). 같은 이름 바꾸기 구멍이 판정 4에도 있다 — #102로 따로 고친다
