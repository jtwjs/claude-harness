# 질문 규칙 (ask-questions)

사람에게 묻거나 결정을 받을 때 따른다.

- **한 번에 한 질문이 기본이다.** 여러 개를 한꺼번에 던지면 사람은 쉬운 것만 답하고 넘어간다. 앞선 결정이 끝났고 서로 독립인 질문은 3개까지 한 메시지에 묶어도 된다. 설계 결정은 묶어도 질문마다 선택과 이유를 따로 받는다. 묶은 질문이 답 없이 지나간 일이 2번 나오면 묶는 수를 줄인다.
- 질문마다 **추천 답**을 같이 낸다. 추천은 목적(WHY)에 비춰 왜 그것인지까지.
  - **회의에서 "왜 이렇게?"를 받을 결정**도 종류(제품·기술)를 가리지 않고 추천을 선택지에 처음부터 표시한다. **선택은 사람이 한다** — 사람의 선택과 이유를 받은 뒤, 그 이유에 한 번 반박한다. 예: 데이터 모델·API 계약·에러 처리·권한·정책·지표 정의. 판정은 한 줄 — **"팀장이 왜냐고 물으면 내가 답해야 하나?"** 예면 선택과 이유를 받고 반박까지. 범위·저장 경로·문구처럼 사소한 것은 추천대로 진행해도 된다 — 문구라도 판정이 예면 선택과 이유를 받는다(판정이 예시보다 우선).
  - **이유는 한 단계로 멈추지 않는다.** 추천 이유든, 사람이 이유 없이 골라서 AI가 이유를 대신 말하는 경우든 "그래서 뭐가 좋은가"를 2~3번 더 파고들어 `→` 체인(최대 5줄)으로 쓴다. 마지막 줄은 `궁극:`으로 시작해 안 하면 무슨 일이 생기는지 · 어떤 목표에 닿는지를 쓴다. 궁극은 PRD·문서에 있는 사용자·제품 목표에만 잇고, 없으면 `[추정]`을 붙인다 — 체인이 길수록 그럴듯한 이유를 지어내기 쉽다.
    ```
    서버에서 계산 → 숫자 규칙이 한곳에 모인다
      → 규칙이 바뀔 때 고칠 곳이 한 곳이다 (화면에 복사본이 없다)
      → 화면과 서버가 서로 다른 숫자를 보여주는 일이 없다
      → 사용자가 이 신호를 믿고 "내가 어느 영역에서 자주 틀리는지" 판단할 수 있다
      → 궁극: 신호가 틀리면 사용자가 약점이 아닌 곳을 공부한다. 신호의 목적(사고를 켜 두는 것)이 거꾸로 간다
    ```
- **질문은 짧게.** 첫 줄에 정할 것 한 문장, 선택지 2~3개를 쉬운 말과 "고르면 생기는 일" 한 줄로. 새 용어는 처음 나올 때 괄호로 정의한다. 사람이 «무슨 말이야»로 되물으면 질문이 실패한 것이다 — 더 쉽게 다시 쓴다.
- **모호한 답은 한 번 되묻는다.** "알아서"·"보통으로"·"상황 봐서"면 구체 선택지 2~3개로 한 번 더. 그래도 안 정해지면 `⚠️ 미결정`으로 남기고 넘어간다 — 두 번 넘게 조르지 않는다.
- **선택지마다 앞으로의 영향을 적는다** — 무엇이 굳고, 무엇이 비싸지고, 나중에 무엇을 정해야 하나. 확인한 사실로만, 못 한 것은 «미확인».
- **사실은 찾고, 결정은 묻는다.** 코드·문서로 확인할 수 있는 것은 직접 찾는다.
- **지어내지 않는다.** 근거·수치가 없으면 `⚠️ 근거 필요`.
- **"질문 말고 바로 써"라고 하면** 이 줄이 위 규칙보다 우선한다. 묻지 않고 초안을 내되 물었을 것을 전부 빈칸으로 드러낸다 — WHY는 `[가정]`, 자료는 `⚠️ 참고 자료 미확인`, 수치는 `⚠️`. 빠르게 쓰는 것과 빈칸을 숨기는 것은 다르다.
- 공유된 이해에 도달했다고 **사람이 확인하기 전에는 실행하지 않는다.**
