# 숫자를 설명한다 (explain-the-number)

재기 전, 그리고 잰 숫자(속도 향상 · 회귀 · 처리량 · 지연 · 평가 결과)를 믿거나 보고하거나 그것으로 정하기 전에 따른다.

- **돌리기 전에 결정을 적는다.** 이 숫자로 무엇을 정하는지, 어떤 결과가 나오면 결정이 바뀌는지, 잡음 바닥(같은 조건을 다시 돌려도 생기는 차이)이 얼마인지. 반복 사이 흔들림이 효과보다 크면 멈춘다. 더 돌려도 결론이 나지 않는다.
- **「왜 두 배는 아닌가?」를 묻는다.** 결과를 묶어 두는 자원이나 코드 경로(제한 요인)를 이름으로 댄다. 실행 중에 뜬 프로파일 · 카운터에서 나와야 하고, 코드를 읽고 짐작한 것은 제한 요인이 아니다.
- **이 숫자가 대신 잰 것일 수 있는 것을 늘어놓고** 하나씩 증거로 지운다. 오류 · 건너뛰었거나 캐시된 일 · 돌지 않은 코드 · 튜닝 안 된 쪽 · 잡음 · 너무 작아서 상관없는 부분.
- **반복 횟수 · 흔들림 폭 · 제한 요인을 숫자와 같이 둔다.** 숫자만 떼어 옮기면 받는 사람은 믿어도 되는지 판단할 수 없다.
- **평가 결과**면 모든 실행이 실제로 과제를 했는지, 차이가 시행 · 모델을 바꿔도 남는지, 그 시나리오가 중요한지를 묻는다.
- **성능 숫자**면 아래 7문항을 돌린다.

## 숫자 점검 7문항

PR의 전후 비교 · 회귀 주장 · 반복 측정 장치 · 라이브러리나 설정 선택처럼 성능 숫자를 낼 때 쓴다. 답마다 코드에 대한 짐작이 아니라 실행에서 나온 증거를 댄다.

먼저 낼 주장을 내보낼 문장 그대로 적는다(예: 「6만 행 데이터에서 내보내기가 p50 기준 30% 빠르다」). 7문항은 그 문장을 시험한다. 재는 스크립트가 무엇을 재고 · 세고 · 무시하는지 읽어 둔다. 기계가 다른 일로 바쁘면 무엇이 도는지 확인하고, 멈출지는 사람에게 묻는다. 멈추지 않으면 양쪽을 번갈아 돌려 같은 잡음을 보게 하고 보고에 적는다.

1. **왜 두 배는 아닌가?** 제한 요인을 댄다. 프로파일러는 일을 느리게 하므로 보고하지 않는 별도 실행에서 뜬다. 부하 생성기도 본다. 그쪽이 먼저 포화하면 부하 생성기를 잰 것이다. 변경이 숫자를 못 움직였으면 제한 요인이 그 이유이니, 쓸모없다고 하기 전에 찾는다.
2. **튜닝됐나?** 모든 쪽을 운영과 같이 돌린다(릴리스 빌드 · 운영 플래그와 환경 · 배치와 트랜잭션 설정 · 커넥션 풀 · 운영과 같은 캐시 상태 · 같은 버전과 데이터). 한쪽만 기본값이면 구현이 아니라 설정을 비교한 것이다. 제한 요인이 설정(행마다 커밋 · 디버그 빌드 · 빠진 인덱스)이면 그쪽은 튜닝 안 된 것이니 튜닝하고 다시 잰 뒤에 승자를 고른다. 튜닝할 수 없으면 그 실행으로 승자를 고르지 않는다. 사람이 무엇을 들일지 고르는 중이면 「지금 출시된 설정 기준」으로 주장을 좁혀도 풀리지 않는다. 들이는 것은 선택지이지 오늘의 설정이 아니다.
3. **한계를 넘었나?** 계산해 본다. 초당 바이트를 디스크 · 네트워크 대역폭과, 초당 연산 × 연산당 비용을 코어 수와, 아낀 시간을 바꾼 부분이 걸린 시간과 견준다. 실행의 10%를 차지하는 부분을 없애면 많아야 약 11% 빨라진다. 한계를 넘은 결과는 일이 아닌 것(캐시 · 아무것도 안 하는 코드 · 버그)을 잰 것이다.
4. **오류가 났나?** 실패와 성공 아닌 응답을 세고, 출력이 있는지가 아니라 맞는지 확인한다. 거절은 빠르고 타임아웃 · 재시도는 느려서 숫자를 양쪽으로 비튼다. 스크립트가 오류를 안 세면 세게 한다.
5. **재현되나?** 각 쪽을 최소 5번, 번갈아(A, B, A, B …) 돌려 워밍업 · 지연 초기화 · 캐시 · 표류가 어느 쪽에도 유리하지 않게 한다. 중앙값과 범위를 보고한다. 반복 사이 흔들림보다 작은 차이는 측정 가능한 차이가 아니다. 아슬아슬하면 순위합 검정이나 측정 장치의 통계를 쓴다.
6. **중요한가?** 미시 결과 옆에 사용자가 기다리는 전체 경로를 실제 크기의 데이터 · 동시성으로 재고, 미시 결과를 전체 중 몫으로 보고한다. 요청의 1%를 차지하는 헬퍼는 아무리 빨라져도 요청을 많아야 1% 빠르게 한다.
7. **일이 실제로 일어났나?** 잰 구간 안에서 일이 돌았는지 확인한다. 요청이 서버에 닿았고, 행이 써졌고, 바이트를 읽었고, 코드가 결과를 썼는지. 아무도 돌리지 않은 제너레이터 · 아무도 기다리지 않은 프로미스 · JIT가 버릴 수 있는 결과 · 타임아웃은 일어나지 않은 일에 숫자를 만든다.

사람이 대략 감만 달라고 했으면 한 번 돌려도 되지만, 4 · 7번은 확인하고 한 번 돌렸다고 적는다. 나머지는 그 실행이 이상해 보일 때만 본다. 선택지 사이의 고르기는 대략 감이 아니다.

보고할 때:

- 판정(빨라짐 · 느려짐 · 측정 가능한 차이 없음 · 판정 불가)을 먼저 낸다.
- 숫자를 단위 · 실행 횟수 · 범위 · 제한 요인과 같이 낸다(예: 「p50 41 ms → 33 ms, 쪽마다 7회 중앙값, 바뀐 뒤 범위 32~35 ms, 한 코어의 JSON 파싱이 제한」).
- 차이를 주장하는데 제한 요인을 못 대거나, 한쪽이 튜닝 안 됐거나, 4 · 7번을 확인 못 했으면 판정 불가로 하고 빈 곳을 이름으로 댄다.
- PR 본문에는 대표 숫자 하나만 두고, 실행 기록 · 범위 · 제한 요인 증거는 링크한 별도 기록에 둔다.
