## ADR-017 앞단 설계 도구는 새 스킬 없이 DESIGN · PLAN 절차와 원칙 문서에 녹인다

- 상태: 수락 (2026-11-25)
- 맥락: 재구성(ADR-016(자동 입구는 몇 개만, 단계 스킬은 경로로 · 원칙은 문서로))은 뒷단(구현 · 리뷰 · 마무리)에 PStack을 들였다. 앞단(설계 · 계획)은 `sdd/references/design.md` · `sdd-plan` · `docs/principles/ask-questions.md`가 맡는다. `mattpocock/skills`(MIT, 39개)를 0.41.0 실물과 대조하니 앞단에 쓸 개념 7묶음이 남았다(`VERDICT.md`). 그중 둘은 하네스 규칙과 정면으로 반대다: 질문 라운드(하네스는 한 번에 한 질문)와 수직 조각(하네스 step은 한 레이어씩 가로 분할).

- 대안(버린 방법):
  - 원본처럼 스킬 단위로 들이기(`grilling` · `domain-modeling` · `to-tickets` …) — 자동 입구와 description이 늘어 ADR-016 D0(입구는 몇 개만)을 되돌린다. 원본도 39개 중 24개가 사람만 부르는 스킬이다
  - step까지 수직으로 — step 하나가 여러 층을 만지면 `sdd-plan` §3 자기완결성과 `sdd-review` 경계 판정 단위가 커진다. 원본에서 수직 조각 단위는 「새 컨텍스트 하나에 들어가는 티켓」이라 하네스의 phase에 더 가깝다(추정)
  - 대상 레포 루트에 살아 있는 용어집 파일 — ADR-013이 버린 「정본 둘」과 같은 모양이고, 새 산출물이라 `harness-init` 템플릿 · `harness-doctor` 검사까지 번진다(D2a)
  - `setup-ts-deep-modules` — TS 전용 도구 설치라 스택과 무관한 플러그인 범위 밖. 필요해지면 스택 팩(`templates/stacks/`)으로
  - 「두 번 설계」(서브에이전트 3개 이상이 서로 다른 인터페이스를 병렬로) — 호출 비용 대비 근거가 없다. `build-the-lever.md`도 여러 에이전트보다 결정적 도구를 먼저 친다
  - 시제품 상세 절차(LOGIC / UI, 약 13KB) — 상태 모델은 `statechart`, 화면은 디자인 트랙이 이미 맡는다. `statechart` 첫 사용 판정(ADR-016 D8) 전에 겹치는 도구를 늘리지 않는다
- 범위 밖 → #52: 「사람은 설계 · 검증(리뷰)에서만 개입」(사용자 원칙, 2026-11-25) 밖의 게이트(PLAN step 승인 · REFLECT 승인 묶음)는 #52 E절 「사람 체크포인트를 세션별로 배치」에서 다룬다
- 주의(지휘 검토):
  - D2의 ADR 3조건 필터는 README 첫 줄 「결정은 ADR로」의 뜻을 좁힌다. 필터를 넣으면 README 문구도 같이 고친다. 3조건을 못 넘어 ARCHITECTURE 한 줄로 가는 결정에도 결정 주체(사용자 / AI 추천 수용)는 적는다
  - D1c의 확인 장치는 #52로 간다. #51 구현은 기준 문장까지만
