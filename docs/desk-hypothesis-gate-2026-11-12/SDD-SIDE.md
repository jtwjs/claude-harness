# SDD-SIDE: 가설 게이트 원장, plugin(sdd) 쪽 설계안

> claude-harness 이슈 #1 (desk-hypothesis-gate)의 plugin 쪽 설계. desk 쪽 PRD·ARCHITECTURE·ADR은 desk 레포에서만 고치고, 이 파일은 이 레포에서만 고친다.
> 상태: 설계안 (구현 전). 2026-11-13.
> 사람 이름·원문·코드는 원장 어디에도 적지 않는다.

## 한 줄 요약

AI에게 맡길 때마다(프롬프트 한 번) 원장에 한 줄을 추가하고, 이유 없는 수락이 기준 횟수만큼 이어지면 가설을 다시 요구한다. 막지는 않고 건너뜀을 기록한다. 쓰는 쪽은 sdd(plugin), desk는 읽기만 한다.

## 결정 표

결정 주체: **사용자** = 선택지 중 직접 고름, **AI 추천 수락** = AI가 낸 추천을 그대로 받음(이유 없음).

## 줄 형식

맡김 줄:

```json
{"ts":"2026-11-13T10:02:00.123456+09:00#a1b2","repo":"<repo>","task":"<task>|null","gate":"schema|api|error|delete|security|null","diff":"easy|mid|hard|null","area":"FE|BE|infra|domain|unknown","hyp":false,"rec":true,"acc":true,"why":false,"rebut":false,"skip":true}
```

적중 줄 (맡김 줄과 섞여 같은 파일에 쌓임):

```json
{"ref":"<원 줄의 ts>","hit":"right|partial|wrong","by":"model|finn"}
```

보정 줄 (sdd REFLECT에서 사람이 확정한 것만, 같은 파일):

```json
{"ref":"<원 맡김 줄의 ts>","gate":"schema|api|error|delete|security|null","by":"finn"}
```

- 보정 줄은 `gate`만 바꾼다. 같은 `ref`가 여러 번이면 마지막 줄이 유효하고, 유효한 `gate`는 보정 줄이 있으면 그 값, 없으면 원 줄 값이다. `by`는 사람이 확정한 경우만 써서 `finn`뿐이다.
- 줄 종류는 키로 가른다: `ts`가 있으면 맡김 줄, `hit`가 있으면 적중 줄, `gate`와 `ref`만 있으면 보정 줄.
- 원장은 추가 전용. 줄을 고치지 않는다.
- 같은 `ref`가 여러 번 나오면 마지막 줄이 유효. `by`는 모델 판정과 사용자 정정의 구분(`finn`은 사용자 정정을 뜻하는 값 이름).
- `hit`는 `hyp=true`인 줄에만 의미가 있다. `hyp=true`인데 `hit` 줄이 없으면 "판정 전".
- 칸은 JSONL이라 나중에 추가해도 desk가 안 깨진다. 단 추가 전에 쌓인 줄에는 값이 비어 있다.
- `ts`는 `<ISO 마이크로초>#<hex 4자리>` 불투명 식별자다(2026-11-13부터. 이전 줄은 밀리초 `ts`). 시각으로 읽으려면 `#` 앞까지 쓴다. `ref`는 이 문자열 통째로 맞춘다.
- `diff` 칸이 줄에 없으면 안 적은 것(이 칸이 생기기 전 줄이거나 모델이 빼먹음), `diff:null`은 적었지만 매길 대상이 없다는 뜻(`hyp=false` 이거나 판정 불가)이다.

## 판정 기준

| 칸 | true일 때 |
|---|---|
| `hyp` | 사용자 본인의 예상이나 가설이 한 줄이라도 있음. "모르겠다"는 false |
| `rec` | 직전 AI 응답에 AI의 추천이나 권장안이 있었고 이 프롬프트가 그에 응답함 |
| `acc` | `rec=true`이고 그 추천을 그대로 받아들임 |
| `why` | 선택의 근거를 설명하는 말이 있음. "기억 안 난다", "모르겠다"는 근거가 아니라서 false |
| `rebut` | 직전 AI 응답이 사용자의 가설에 반박이나 이견을 냈음 |
| `skip` | 재요구 상태가 켜진 동안 가설 요구를 받았는데 `hyp=false`로 넘어감 |
| `diff` | 가설을 맞히기 어려운 정도. 범위(여러 레이어에 걸침), 되돌리기 어려움(마이그레이션·삭제·공개 API 계약), 선례 없음(레포에 같은 패턴이 없음) 중 하나라도 해당하면 `hard`, 하나도 아니면 `easy`, 애매하면 `mid`, `hyp=false`면 `null` (참고용) |

## 계산 규칙 (원장 줄 순서만으로 계산, 별도 상태 파일 없음)

맡김 줄만 순서대로 훑는다(적중 줄 제외). 단위는 (repo, task).

```
연속 값   같은 (repo, task) 안에서 rec=true AND acc=true AND why=false 인 줄이 이어진 횟수
          why=true 줄이나 (repo, task) 변경에서 0
          gate=null 줄과 task=null 줄은 세지도 끊지도 않음 (gate는 보정 줄이 있으면 마지막 보정 줄의 값)
재요구 상태  연속 값이 기준 횟수(config)에 닿으면 켜짐
          연속 값이 0이 되어도 켜진 채 유지
          켜진 뒤 같은 (repo, task) 안에서 hyp=true 줄과 rebut=true 줄이 (순서 무관) 모두 나오면 둘째 줄에서 꺼짐
          (repo, task)가 바뀌면 모은 것을 버림
```

## 구성 (구현 전, 모두 새로 만들어야 함)

확인함: `hooks/hooks.json`의 이벤트는 `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `SessionStart`, `Stop`뿐이고 프롬프트 시점 이벤트(`UserPromptSubmit`)가 없다. 맡김 줄을 쓰는 코드와 연속 값 상태도 없다.

```
UserPromptSubmit 훅 (새로 추가)
  ├─ 원장을 훑어 재요구 상태 계산
  ├─ 켜졌으면 모델에게 "가설을 먼저 받고 진행하라" 한 줄 주입 (꺼졌으면 주입 없음, 토큰 0)
  └─ 모델이 이 프롬프트의 gate·area·hyp·rec·acc·why·rebut·skip을 판정해 줄 한 개를 쓰도록 지시
작업 후 보정 (sdd REFLECT에서 gate=null 줄과 diff를 대조해 후보를 보이고 사람이 확정, 보정 줄로 기록)
적중 줄 쓰기 (sdd REFLECT에서 모델이 제안, 사람이 정정)
```

## 되는 것

- 맡길 때마다 줄이 자동으로 남는다(모델이 판정을 선언하는 한).
- 재요구 상태를 줄 순서만으로 계산한다. 별도 상태 파일이 필요 없다.
- 막지 않고 건너뜀을 기록한다.
- desk는 읽기만 하고, 칸이 늘어도 안 깨진다(JSONL).
- sdd 안팎의 맡김을 같은 규칙으로 센다.

## 안 되는 것

- 훅이 가설 요구를 강제하지 못한다. 모델이 무시하면 `skip`으로 남을 뿐이다.
- 모델이 판정 선언을 빼먹으면 그 프롬프트의 줄이 조용히 누락된다. 확인 장치를 두지 않기로 했으므로(결정 표 「줄 쓰는 방법」) 누락은 측정으로만 본다. 누락이 연속 값을 끊거나 줄이므로 재요구가 늦게 켜질 수 있다.
- `task=null`(sdd 밖) 맡김만으로는 재요구 상태를 못 끈다. 켜진 채 sdd 밖에서만 일하면 요구가 계속 간다. 같은 이유로 sdd 밖 맡김은 연속에도 안 세진다(결정 표 「`task=null` 맡김의 연속 계산」). 작은 작업은 sdd를 건너뛰므로 큰 작업만 감시되는 설계다.
- 기준 횟수를 이 설계가 정하지 않는다. 기준 기간(2~4주)이 지나야 사용자가 정한다.
- 원장을 잘라내거나 회전하면 재요구 상태가 사라진다. 전체 보존이 전제이고, 정리가 필요하면 그 시점 상태를 한 줄로 남기는 안이 필요하다.
- 기준 횟수를 config에서 읽을 때 가져오므로, 값을 바꾸면 과거 상태도 새 기준으로 다시 계산된다.

## 미확인

- 게이트 보정이 어느 줄을 고칠지 찾는 방법. 원장에는 프롬프트 원문이 없고 맡김 줄은 `ts`와 판정 칸뿐이다. REFLECT 때 모델이 같은 세션 맥락으로 `gate=null` 줄이 어느 프롬프트였는지 알아야 하는데, 세션이 압축됐거나 이어서 열렸으면 모를 수 있다. `미측정: 압축 뒤 REFLECT에서 줄을 프롬프트에 대응시킬 수 있는지 실제 세션으로 확인 / 구현 마지막 단계`.
- `hyp rec acc why rebut`을 모델이 얼마나 맞게 판정하는지. `미측정: 줄이 쌓인 뒤 샘플 20건을 사용자가 대조 / 첫 2주 안`.
- 줄 누락률(프롬프트 수 대비 줄 수). `미측정: 세션 기록의 프롬프트 수와 원장 줄 수를 대조 / 첫 2주 안`.
- 판정 호출이 맡길 때마다 늘리는 토큰 양. `미측정: 프롬프트 몇 건에 판정을 돌려 토큰 로그로 재기 / 구현 첫 단계`.
- 프롬프트 시점 훅이 이 환경에서 모델 컨텍스트에 한 줄을 실제로 주입하는지. `미측정: 훅 하나 만들어 확인 / 구현 첫 단계`(추정: 가능).
- 매 프롬프트마다 원장을 훑는 시간. `미측정: 줄 수천 개로 훅 시간 재기 / 구현 첫 단계`.
- 쓰기 중 줄이 꼬이는지(동시에 두 훅이 추가할 때). `미측정: 동시 실행으로 재기 / 구현 단계`. 추가 전용 한 줄 쓰기라 낮다고 추정.
- `area` 판정의 정확도와, 한 프롬프트에 영역이 둘 이상일 때의 처리(지금은 단일값).
- 여러 레포의 hook이 전역 파일 하나를 동시에 쓸 때의 경합.
- sdd를 거치지 않은 설계 성격 맡김(`task=null` 이면서 `gate`가 null이 아닌 줄)이 얼마나 되는지. 이 줄은 연속에 안 세져 이유 없는 수락이 샐 수 있다. `미측정: 원장에서 그 조건의 줄 수 / 전체 줄 수 / 첫 2주 안`. 비율이 크면 `task=null`을 레포 단위로 세는 안을 다시 검토.

## desk와 맞춘 것

- 적중 값은 `right|partial|wrong` 3값 영문 그대로. 이름 매핑(맞음/부분/틀림)은 desk 화면에서 한다. "모르겠다"는 적중 값에 없다(가설 칸에 모르겠다는 `hyp=false` 줄이고 `hit` 줄이 없다).
- 단위는 (repo, task) 쌍.
- `hit` 줄은 `ref`로 원 줄을 찾아 `area`를 가져온다.
- "이유 없이 수락" 비율은 desk 쪽에서 `gate=null` 줄을 분모와 분자에서 뺀다.
- 서로 상대 파일은 고치지 않는다. desk 문서가 이 설계를 가리킬 때는 "sdd 쪽 설계안 참고"로만 적는다.

## desk가 맞춰야 할 것 (아직 안 알림, 2026-11-13 기준)

- 보정 줄 `{"ref","gate","by"}`을 합쳐 읽는다. `ref`로 원 줄을 찾아 유효한 `gate`를 쓴다.
- 「이유 없이 수락」 비율에서 빼는 `gate=null` 판단도 유효한 `gate` 기준이다.
- 보정은 나중에 붙으므로 같은 원 줄의 `gate`가 시간이 지나며 바뀔 수 있다.
