# ADR — vault 맞춤 정리 (vault-align 트랙)

> 번호는 지휘(`conductor`)가 발급했다. 결정 원문은 GitHub 이슈에 있다.

## ADR-010 새 규칙을 더하면 기존 코드 정리까지 — 지휘 절차로

- 상태: 수락 (2026-11-23)
- 맥락: 트랙이 새 규칙(린트 · 테스트 · 규칙 파일)을 더하고 기존 위반을 남기면, 규칙과 지금 코드가 다른 말을 한다. 2026-11-23 stack-kits 린트 작업에서 정리에 키트 src까지 범위가 필요했고 지휘가 승인으로 처리했다(첫 사례). 결정 이슈 #20, 전파 #21.
- 결정: 새 위반을 먼저 막고 → 기존 위반 목록 → 기존 코드 고침 → 0건 출력까지 같은 작업에서 한다. 남은 위반은 지휘가 `follow-up`으로 낸다. 정본은 `skills/conductor/SKILL.md` §5 「새 규칙 → 기존 코드 정리」, 소유 경로 확장은 §6 「새 규칙 위반 정리만」 판정. track-brief 템플릿 「금지」 · 「끝나면 지휘에 보고」 4번에 한 줄씩.
- 결정 주체: 사람(지휘 절차로 두기) · 자리(conductor 스킬)는 AI 추천 수용
- 대안: sdd 마무리 단계 게이트(하네스 없는 레포는 빠지고 작업이 큼 — 직접 연 세션에서 빠지는 일이 실제로 생기면 더한다) / 린트 래칫(CI 건수, 글 규칙은 못 잡음)
- 결과: 지휘가 연 트랙에만 걸린다. 사람이 직접 연 세션은 이 절차를 모른다.

## ADR-011 설계 결정에서도 AI 추천을 선택지에 처음부터 표시

- 상태: 수락 (2026-11-23)
- 맥락: 옛 규칙은 "왜?"를 받을 결정에서 사람 생각을 먼저 받고 추천은 뒤에 냈다(근거: 한 인터뷰 5문항 5/5 추천 수용). 결정 이슈 #22, 전파 #23.
- 결정: 추천을 선택지에 처음부터 표시한다. 선택은 사람이 하고, 사람의 선택과 이유를 받은 뒤 한 번 반박한다. 정본은 `skills/why/SKILL.md` 「질문 규칙」. `sdd`(SKILL.md · references/design.md) · `harness` 요약은 정본 문구를 따른다.
- 결정 주체: 사람
- 대안: 옛 규칙 유지(생각 먼저 · 추천은 뒤) — 사람이 바꾸기로 함
- 결과: 추천을 이유 없이 그대로 고르는 일이 다시 늘 수 있다. 가설 원장 `acc` · `why` 지표로 지켜본다.

## ADR-012 지휘 1 + 작업 N 운영 — 판정함 직행 · 권한 모드 auto 통일

- 상태: 수락 (2026-11-23)
- 맥락: 2026-11-23 하루 판정함 질문 17건이 전부 작업 세션에서 나왔고, 그중 교차 7 · 트랙 안 10(지휘 분류, 추정). 세션 간 메시지 17건 중 5건 보류 · 1건 만료가 모두 권한 모드가 다른 세션 사이에서 났다. 작업 세션이 전역 설정을 바꾼 것을 지휘가 사후에 알았다. 결정 이슈 #24, 전파 #25.
- 결정: 설계 질문은 작업 세션이 판정함에 직접 올리고 사용자가 고른다. 지휘는 결정하지 않고, 범위=교차(결과가 그 레포 밖을 바꿈)로 골라진 것만 이슈 · 전파 · ADR 번호로 처리하며 턴 시작에 레포마다 `picks --new`를 본다. 작업 세션은 소유 경로 밖을 사용자가 직접 시켜도 먼저 지휘에 보고한다. 지휘 · 작업 세션 모두 권한 모드 `auto`. 정본은 `skills/conductor/SKILL.md` 「세 자리 역할」 · §1 · §5 · §8, track-brief 「진행 방식」 · 「금지」. 판정함 형식은 desk `decision-inbox` 스킬.
- 결정 주체: 사람(B · auto, AI 추천 수용)
- 대안: A 전부 지휘로(병목 · 코드 맥락 재설명) / C 지휘가 먼저 분류(질문마다 한 단계 더) / 지휘 plan + 작업 bypass(plan은 지휘 쓰기가 막히고 모드가 달라 메시지 보류)
- 결과: 판정함 「범위」 칸은 desk 쪽 변경이 따로 필요하다(jtwjs-desk 이슈). 트랙 안 결정은 지휘 기록에 남지 않는다.

## ADR-013 레포에 `_brain/`을 두지 않는다 — brain-sync · brain-walk · `_brain` 템플릿 제거

- 상태: 수락 (2026-11-23)
- 맥락: brain-sync 대상 폴더가 vault에서 없어져 auto 이관이 이미 조용히 꺼져 있었다(부모 폴더 검사에서 끝남). 활성 레포(jtwjs-desk · claude-harness)에는 `_brain/`이 없다(확인). 「왜 그렇게 했나」는 레포별 ADR이 이미 맡는다. 결정 이슈 #26, 전파 #27.
- 결정: 하네스는 레포에 `_brain/`을 깔지도 쓰지도 않는다. 스킬 `brain-sync` · `brain-walk`, 훅 `brain-sync-auto`, `templates/_brain/` · `templates/.claude/rules/brain.md`, sdd REFLECT 「지식 정리」의 이관 단계, cadence 축 2, pr-write 4.95의 tables.md 기록, harness-init ⑤ 질문, harness-doctor 7-d, `harness.json` `brainSync` 키를 걷어냈다. 제품·도메인 결정은 기능 PRD 「결정」 절, 기술 결정은 ADR이 정본이다. 「기록은 한 건 = 파일 하나」 규칙은 `sdd` ④-1(회고)로 옮겨 쌓기만 하는 기록 전체로 넓혔다. 회고 위치는 `docs/retro/`. harness-init 업그레이드 모드는 기존 레포의 `_brain/`을 지우지 않고 안내만 한다. `hooks/tests/no-brain.sh`가 참조 0을 지킨다.
- 결정 주체: 사람
- 대안: 허브에 링크만 / 새 칸으로 사본(정본이 둘이 되거나 쓰는 곳이 없음) / brain-sync만 제거하고 나머지는 별도 PR(사람이 한 번에 정리하기로 함)
- 결과: 공개 스킬 2개 · 훅 1개가 사라진다. 이미 `_brain/`이 있는 레포는 아무도 갱신하지 않는 문서로 남는다. 도메인 용어 · 비즈니스 흐름 구조화는 지휘 자리 쪽 별도 작업. `hooks/test.sh`는 고치지 않는 규칙이지만, 지운 훅·템플릿을 가리키던 케이스(6-c 등)는 지우거나 경로를 바꿀 수밖에 없어 이 PR에서 고쳤다.
