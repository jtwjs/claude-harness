# ADR — 설계 단계 보강 (design-phase 트랙)

> 번호는 지휘(`conductor`)가 발급한다. 결정 원문은 jtwjs/claude-harness 이슈 #76과 지휘 전달이다. 이번 범위는 판정 문서까지이고, 구현은 사용자가 고른 것만 #52(검증 흐름, PR #78 64dc118로 머지) 판 위에서 이슈로 나눈다. 줄 번호는 64dc118 기준이다.

## ADR-022 설계 결정은 지휘 한 곳에서, 사람은 설계서 하나를 읽고 고친다

- 상태: 수락 (2026-11-26). D6 · D1 · D7 · D2(설계서) · D3 · D5(P6 포함)는 사용자 결정
- 용어: 「세컨드브레인」은 사용자 개인 지식 저장소다. 개인화된 하네스라 이름을 드러낸다(사용자 결정). 공개 레포에는 사람 이름 · 개인 경로 · 세컨드브레인 원문을 쓰지 않는다. 「설계서」는 사람이 읽고 고치는 설계 문서 한 장이다(D2). 레포의 PRD · ARCHITECTURE · ADR은 에이전트가 읽는 문서로 남는다.
- 맥락: 설계 문서는 사람이 직접 읽고 고쳐야 한다(사용자 원칙, #76). 지금 설계 단계에서 사람은 결정 질문에 답하고, 문서는 AI가 반영한 채로 확정된다(`skills/conductor/references/decisions.md:10` · `skills/sdd/references/design.md:42`). 외부 요구사항 정리 방식(AI 초안 → 사람 검수 · 수정 → AI 재검토 → 짚은 항목에 한 번에 답 → 최종본)과 공개 스킬 묶음 둘의 묻는 법을 대조했다. 외부 방식의 원 대조표는 레포에 두지 않는다. 여기에는 일반화한 판정과 레포 근거만 적는다. 대조 중에 지휘 역할과 설계 담당 경계가 부딪히는 것이 드러나 사용자가 먼저 정했다(D6).
- 대체 · 갱신:
  - ADR-014(설계는 지휘에서 끝내고 맡긴다)를 좁힌다: 「설계 결정은 지휘에서(사용자가) 정하고, 문서 초안 · 코드 조사는 코드 옆에서」(D6)
  - ADR-019(만드는 세션과 검증하는 세션을 나누고, 사람은 설계와 검증 자리에서만 본다) E4 「PRD는 지휘가 결정 이슈 본문에 쓴다」 → 「지휘는 설계서를 쓰고, PRD는 검증 세션이 설계서로 쓴다」(D2)
  - ADR-019 E5 「PRD 옮김 → ARCHITECTURE · ADR만」 → 「설계서 최종본으로 PRD · ARCHITECTURE · ADR을 쓴다. 그 안의 결정은 설계서 결정 칸을 거친다」(D2 · D6)
  - ADR-017(앞단 설계 도구는 DESIGN · PLAN 절차와 원칙 문서에 녹인다) D7(한 번에 한 질문 + 독립 질문 3개까지)을 대체한다(D1)
- 겹침: #52가 만든 「PRD를 받았을 때」 갈래(`skills/sdd/SKILL.md:43` · `design.md:11`)와 「PRD는 지휘가 쓴다」 · 결정 이슈 「PRD」 칸(`decisions.md:23,38-42`)이 D2로 바뀐다. #77(나눔 모드 재판정이 「테스트가 틀렸다」일 때 러너 진행 길)은 같은 흐름의 뒤쪽이라 분해 표 옆에 같이 둔다.
- 갱신: #87 (2026-11-28, 사용자 — AI 추천 수용) — D2 설계서 틀을 간단히 · 자세히 · 아주 자세히 + 우리 칸으로 바꾼다. 설계서 순서 3: 큰 방향(구조 상자 · 큰 선택)은 설계서에서 묻고, 코드 근거가 필요한 선택은 결정 묶음으로 넘긴다. 「설계서와 세 장」: PRD는 설계서 칸에서 뽑고 세 장 줄마다 출처 칸을 단다. 칸 순서 검사를 설계서를 화면에 열기 전에 돌린다. 근거: docs/design-doc-format-2026-11-28/

### D6 지휘 역할과 설계 담당 경계 (사용자 결정)

부딪힌 곳: 지휘 결정 흐름은 「설계는 지휘에서 끝내고, 설계 문서가 확정된 뒤 디스패치」(`decisions.md:7-9`)이고, ADR-019 E4 · E5는 「지휘는 PRD만, ARCHITECTURE · ADR은 검증 세션」이다. #52 판에 둘이 같이 들어가 있다.

결정:

1. 사람이 읽는 설계 문서(설계서)는 지휘가 사용자와 쓴다. 세컨드브레인 맥락이 지휘 자리에만 들어온다. (처음 결정의 「PRD는 지휘가 쓴다」는 D2로 「설계서는 지휘, PRD는 검증 세션이 설계서로」가 됐다)
2. 레포 문서(PRD · ARCHITECTURE · ADR)는 검증 세션이 코드를 보며 쓴다. 그 안의 결정은 혼자 정하지 않고, 파일:줄 근거를 붙인 결정 묶음(D2 꼴)으로 지휘에 올린다 → 지휘가 설계서 「결정」 칸에 넣고 사용자에게 → 회신. 지휘는 코드를 깊게 읽지 않는다(`decisions.md:11` 「코드 사실은 작업 세션」 유지).
3. 관문 둘: 디스패치 = 설계서 최종본 뒤 / 구현 시작(계획 쪼개기 포함) = 구조 · 기술 결정 「정할 것」 0. 둘째 관문은 글이 아니라 장치로 거는 안을 구현 이슈 후보로 둔다(J5, 사용자 방향: 규칙보다 린트 · 훅).
4. 지휘 역할은 아래 표로 좁힌다.

| 일 | 남김 / 옮김 | 어디서 | 이유 |
|---|---|---|---|
| 디스패치 · 우선순위 | 남김 | 지휘 | 트랙 여럿을 한 자리에서 봐야 겹침 · 순서를 안다 |
| 사용자 질문 모으기(판정 거르기, `decisions.md:14-21`) | 남김 | 지휘 | 사용자가 답하는 자리가 한 곳이어야 한다 |
| 결정 기록 · ADR 번호 | 남김 | 지휘 | 번호와 결정 정본은 한 곳(`skills/conductor/SKILL.md:16`) |
| 관문 둘(디스패치 · 구현 시작) | 남김 | 지휘(둘째는 장치 후보) | 다 정하기 전 구현을 막는 자리(ADR-014가 고친 사고) |
| 설계서(사람이 읽는 설계 문서) | 남김 | 지휘 | 세컨드브레인 맥락이 지휘에만 붙는다 |
| 세컨드브레인 기록 · 트랙 보고 확인 · 세션 간 중계 | 남김 | 지휘 | 트랙 보고 4칸을 지휘가 자리 쪽으로 넘긴다(ADR-019 G4) · 초인종(§8) |
| 레포 문서(PRD · ARCHITECTURE · ADR) | 옮김 | 검증 세션 | 코드를 보며 써야 파일:줄 근거가 붙는다. 결정은 설계서 결정 칸 경유 |
| 코드 조사 · 리서치형 답 | 옮김 | 작업 세션 | 지휘는 코드를 깊게 읽지 않는다(`decisions.md:11`) |
| 감독 · 확인 모음 | 옮김(지휘 재설계 뒤) | 장치 | 사람 · 모델이 아니어도 되는 확인은 장치가 한다[추정, 재설계에서 판정] |

감수하는 것:
- 기술 결정 한 건이 트랙 → 지휘 → 사용자 → 지휘 → 트랙으로 왕복한다. `미측정: 결정 묶음 한 건의 왕복 대기 시간 / 수락 뒤 첫 기능`
- 지휘에 중계 글이 쌓인다
- 중계하며 뉘앙스가 빠진다. 결정 묶음에 원문 위치(파일:줄)를 같이 둬서 줄인다
- 둘째 관문이 글로만 있으면 ADR-014가 고친 「다 정하기 전 구현」이 다시 난다(J5가 받는다)

버린 방법: 설계 전용 세션을 따로 연다. ADR-014가 이미 버린 대안 C와 같고(세션이 하나 더 생기고 설계 대화가 지휘 밖으로 흩어짐), D6은 새 세션 없이 검증 세션을 쓴다.

### D7 세컨드브레인 연결을 어디서 까나 (사용자 결정)

사용자 방향: 개인화된 하네스이기도 하니 세컨드브레인과 잇는다고 드러내고, 실제 연결은 설치로 되게 한다.

결정 C:

| 자리 | 하는 일 |
|---|---|
| 지휘 자리 init(`harness-init` 「지휘 자리 모드」, 새로) | 세컨드브레인 경로를 물어 사용자 설정(`~/.claude/conductor.json`, 예: `secondBrain` 칸)에 적는다 → 지휘 자리 `CLAUDE.md` 개인 맥락 칸에 세컨드브레인 쪽 지휘 규칙 연결 줄(`@`) → 세컨드브레인 보드 시작 훅. 지휘 자리 템플릿(역할 · 절차 지도 표 · effort 기본값 · 개인 맥락 칸)을 까는 일과 같은 자리 |
| 레포 init | 「이 레포의 허브가 세컨드브레인에 있나」만 확인한다(허브 쪽 `repo` 키로). 없으면 지휘에 「허브 만들기」를 알린다. 레포(`harness.json` 등)에는 경로를 쓰지 않는다 |
| `harness-doctor` | 경로가 살아 있나 · 보드 훅이 도나 · 규칙 파일이 있나 |

- 같이 닫힘: 세컨드브레인 쪽 지휘 규칙 파일은 그대로 두고 지휘 자리 템플릿이 연결 줄로 가리킨다(바뀌는 링크 0).
- D6과의 관계: 세컨드브레인을 읽는 자리는 지휘 하나다. 검증 · 작업 세션은 읽지 않고, 필요한 사실은 결정 묶음의 「세컨드브레인 관련 사실」 칸으로 지휘가 넘긴다.
- D2와의 관계: 지휘 자리에 세컨드브레인이 연결돼 있으면 설계서 초안 전에 그 레포 허브 맥락(정의 · 지금 아는 것 · 반대 근거)부터 읽는다.
- 버린 방법: 레포마다 `harness.json`에 허브 경로(공개 레포에 개인 경로가 들어가고, 작업 세션이 세컨드브레인을 직접 읽게 되어 D6과 겹친다) / 지휘 자리만 연결(새 레포에 허브가 없으면 첫 설계 맥락이 빈다)

#### 반대 근거 (ADR-017)

결정당 왕복은 라운드가 적었다(0.75 vs 1.17). 표에 없던 결정 2개는 한 번에 한 질문에서, 이유가 담긴 답 끝에서만 나왔다(`docs/design-tools-2026-11-25/COMPARE.md:69,72,84`). 1명 1회 · 주제 크기 차 · 순서 효과로 체감치다(`COMPARE.md:80`). 원본도 같은 반대를 「frontier가 막는다, 다만 판단이라 샐 수 있다」로 답한다(`docs/productivity/grilling.md:31,57-58`). 하네스에서 라운드를 이미 쓴 곳도 있다: 지휘 설계 초안 질문 블록 5개를 한 번에 보내 5/5 답을 받았다(`decisions.md:10`, 1회).

#### 결정: A 라운드 + 막는 장치 셋

선행 결정이 끝난 질문을 한 라운드에 묻는다. 막는 장치:

1. 질문마다 답 칸에 「선택 + 이유 한 줄(있으면)」. 채팅은 `1 B — 이유`, plannotator는 `Note:`
2. 다음 라운드를 짜기 전에 받은 이유에서 새 갈래(표에 없던 결정)를 찾아 넣는다. frontier 다시 계산의 입력이다
3. 물러서는 조건: 라운드에서 답 없이 지나간 질문이 2번 나오거나, 설계 결정이 이유 없이 전부 추천 수용으로 끝난 라운드가 2번 이어지면 남은 설계 결정은 하나씩 묻는다. 사람이 「하나씩」이라고 하면 바로 하나씩

```
라운드 → 결정 하나에 드는 왕복이 준다(ADR-017 0.75 vs 1.17, 원본 13문항 약 3라운드)
  → 사람의 시간이 질문 응답보다 설계서 읽기 · 고치기로 간다(D2)
  → 하나씩의 장점(이유에서 새 결정이 나옴)은 이유 칸 + 새 갈래 찾기로 라운드 안에 옮긴다
  → 물러서는 조건이 있어 수동적으로 끄덕이는 라운드가 이어지면 하나씩으로 돌아간다
  → 궁극: 사람이 자기 말로 설명할 수 있는 계획(design.md:5)을 더 적은 왕복으로 얻는다
```

- 결정: A(사용자, AI 추천 수용, 2026-11-26). ADR-017 D7을 대체한다.
- 버린 안: B 지금대로(한 번에 하나 + 독립 질문 3개까지. 원본 두 묶음과 다른 쪽에 남는다) / C 설계 결정만 하나씩(설계 결정이 대부분인 세션에서 B와 같다)
- 라운드가 도는 자리는 D2의 설계서 재검토(번호 질문)다. 결정 묶음 하나가 곧 한 라운드다.
- 사용자 개인 응답 규칙에도 같은 질문 규칙 줄이 있다. 레포 밖이라 이 ADR은 고치지 않는다.
- 측정: 다음 설계 세션 2회에서 `COMPARE.md` 「재는 것」 표의 지표(질문 수 · 라운드 수 · 표에 없던 결정 · 이유 없이 추천 수용)를 같은 꼴로 남긴다. `미측정: 위 지표 / 수락 뒤 첫 설계 세션 2회`

### D2 설계서, 사람이 읽고 고치는 설계 문서 (사용자 결정)

전제 정정: 「plan mode일 때만 plannotator」 조건은 레포에 없다. plan mode에서 뜨는 것은 plannotator 설치 훅(ExitPlanMode 권한 요청)의 기본 동작이다. 레포는 이미 「도구가 있으면」으로 가르고(`design.md:42`), 지휘는 plan mode를 쓰지 않는다(`decisions.md:10`). 원본도 인터뷰 중에는 plan mode를 끄라고 한다. plan mode는 계획을 서둘러 내게 해서다(`docs/productivity/grill-me.md:19`).

- 지휘 경로: `decisions.md:10` 「설계 초안 받기」. 결정 초안 `.md`(질문 블록 + 추천) → plannotator `annotate` `gate:true` → 사용자 Send → 결정 이슈 · PRD(결정 이슈 본문, `decisions.md:23`)에 반영 → 디스패치 → 검증 세션이 PRD를 옮기고 ARCHITECTURE · ADR을 쓴다(`skills/sdd/SKILL.md:43`). 없는 것: (가) 사람이 설계 문서 자체를 고치는 자리 (나) 사람이 고친 뒤 AI가 다시 보는 한 바퀴 (다) 구조 결정의 근거를 사람이 보는 자리

### D3 설계서 검수에 plannotator를 어떻게 쓰나 (사용자 결정)

D2로 사람이 보는 문서는 설계서 한 장이 됐다. 남은 것은 그 한 장을 어떤 화면으로 주고받나다. 지금 지휘가 plannotator를 쓰는 자리는 결정 초안 한 줄(`decisions.md:10`)이고, 위 「규칙과 실제가 어긋난 사례」처럼 규칙만으로는 열리지 않았다.
