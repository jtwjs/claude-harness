# Systematic Debugging

## 철칙 (The Iron Law)
```
근본 원인 조사 없이는 어떤 수정도 없다.
증상만 고치는 것은 실패다. 규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다.
```
- 간단해 보여도, 급해도, "일단 이것부터" 상황일수록 반드시 적용합니다.
- 코드 수정 자체는 karpathy-guidelines(surgical/verify)를 따릅니다. 여기서는 **디버깅 규율**만 다룹니다.

## 4단계 (앞 단계를 끝내기 전 다음 단계로 넘어가지 않습니다)

**1. 근본 원인 조사**
- 에러 메시지·스택 트레이스를 끝까지 읽습니다 (줄번호·경로·코드). 답이 거기 있는 경우가 많습니다.
- 재현: 매번 재현되는가? 안 되면 추측하지 말고 데이터를 더 모읍니다.
- 최근 변경 확인: `git diff`, 최근 커밋, 의존성·설정·환경 차이.
- **경계 계측 (다중 컴포넌트 시스템: API→서비스→DB, CI→build→sign 등)**: 수정 전에, 각 경계에서 들어온 값/나간 값/환경 전파를 로그로 찍고 **한 번 실행해 어디서 깨지는지 증거를 확보**한 뒤 그 컴포넌트만 파고듭니다.
- **역방향 추적 (에러가 콜스택 깊은 곳일 때)**: 잘못된 값이 어디서 왔는가 → 무엇이 그 값으로 호출했는가 → 발원지까지 거슬러 올라갑니다. 필요하면 위험 연산 직전에 `new Error().stack` + 컨텍스트를 `console.error`로 찍습니다. **증상 지점이 아니라 발원지에서 고칩니다.**

**2. 패턴 분석**
- 같은 코드베이스의 정상 동작 예시를 찾습니다. 참조 구현이 있으면 훑지 말고 전부 읽습니다.
- 정상 vs 고장의 차이를 아무리 사소해도 전부 나열합니다 ("그건 상관없을 것"이라 단정 금지).

**3. 단일 가설 검증**
- 가설을 하나만, 구체적으로 명시합니다: "Y 때문에 X가 근본 원인이라고 본다."
- 가설을 검증할 **가장 작은 변경 하나**만 합니다. 한 번에 한 변수.
- 맞았으면 4단계로. 틀렸으면 **위에 수정을 쌓지 말고** 새 가설을 세웁니다.
- 모르면 "X를 이해 못 함"이라고 말하고 더 조사하거나 도움을 요청합니다.

**4. 근본 원인 수정**
- 재현 실패 테스트를 먼저 만듭니다(기존 TDD-guard/테스트 스킬 활용).
- 근본 원인만 고치는 **단일 변경**. "온 김에" 개선·리팩터 금지.
- 검증: 테스트 통과? 다른 테스트 안 깨짐? 이슈 실제 해결?
- 여력 있으면 각 계층에 방어 검증(defense-in-depth)을 추가합니다.

## 3-Fix 규칙
- 수정이 안 먹히면 **STOP**하고 지금까지 시도한 횟수를 셉니다.
- 3회 미만 → 새 정보로 1단계 재분석.
- **3회 이상 → 4번째 수정 금지. 아키텍처를 의심합니다.** (수정마다 다른 곳에서 새 문제/결합이 드러남 = 잘못된 가설이 아니라 잘못된 구조.) 계속 고칠지 vs 구조를 바꿀지 먼저 논의합니다.

## Red Flags — 이 생각이 들면 1단계로 돌아갑니다
| 합리화 | 실제 |
|--------|------|
| "일단 빨리 고치고 나중에 조사" | 첫 수정이 패턴을 정합니다. 처음부터 제대로. |
| "이것저것 바꿔서 되나 보자" | 뭐가 통했는지 못 가림. 새 버그 유발. |
| "여러 개 한꺼번에 고치면 빠름" | 격리 불가. 한 번에 하나. |
| "급하니 프로세스 생략" | 체계적 디버깅이 삽질보다 **빠릅니다**. |
| "참조가 길어서 대충 각색" | 부분 이해 = 버그 보장. 전부 읽기. |
| "문제 보임, 바로 고치자" | 증상 목격 ≠ 근본 원인 이해. |
| "한 번만 더 시도"(2회+ 실패 후) | 3회+ = 구조 문제. 고치지 말고 의심. |

관련 신호(파트너가 "그거 진짜 그런가?" "추측 그만" "막힌 거야?")가 나오면 추측 중이라는 뜻 → 1단계로.
