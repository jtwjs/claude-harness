작성 원칙: 사용자 영향 큰 변경을 두괄식 상단에, 리팩토링·테스트는 후순위, 단순 변수명·구조 변경은 제외. (상세 지침은 5단계 본문 템플릿의 "변경 사항" 주석 참조 — 중복 서술 금지)

**원칙**: 판단 전에 `${CLAUDE_PLUGIN_ROOT}/docs/principles/INDEX.md`를 보고, 쓰는 원칙은 원문을 읽는다.

## 1단계: 변경 내용 수집

기준 브랜치: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/base-branch.sh"` 출력 = `<base>`. exit 2면 사람에게 묻는다.

```bash
git log <base>..HEAD --oneline          # 커밋 목록
git diff --name-only <base>...HEAD      # 변경 파일 목록
git diff <base>...HEAD                  # 전체 diff
git status --short                       # 미커밋 변경 확인
```

미커밋 변경이 있으면 PR 생성 전에 커밋 여부를 사용자에게 확인한다.

**현재 브랜치가 `<base>` 자신이면**(base 에 바로 커밋이 쌓인 경우) `<base>..HEAD` 가 비거나 틀린다 → `${CLAUDE_PLUGIN_ROOT}/skills/pr-write/references/base-branch-rescue.md` 절차로 작업 브랜치로 옮긴 뒤(사용자 확인 필수) `origin/<base>` 기준으로 계속한다.

## 2단계: 원격 브랜치 푸시

현재 브랜치가 원격에 없거나 뒤처져 있으면 push한다:

```bash
git push -u origin HEAD
```

## 3단계: PR 제목 결정

제목은 커밋 메시지 형식과 같다 — `<type>: 요약`, 괄호 스코프는 `harness.json`의 `git.commitScope`가 `true`일 때만(**정본은 `commit` 스킬**). 예: `feat: 다건 이미지 DnD/paste 업로드 optimistic UI 적용`

## 4단계: Assignee·Label 결정

**Assignee**: `git config user.name` 또는 `gh api user --jq .login`으로 현재 작업자의 GitHub 로그인을 가져와 설정한다.

**Label**: `${CLAUDE_PLUGIN_ROOT}/skills/pr-write/references/labels.md`를 읽고 유형 · 복잡도 두 축에서 1개씩 고른다(레포에 라벨이 없을 때도 그 파일대로).

## 4.5단계: Risk Score 산출 (5축 0~100)

`${CLAUDE_PLUGIN_ROOT}/skills/pr-write/references/risk-score.md`의 5축(보안 30 · 스코프 20 · Breaking 20 · 테스트 15 · 마이그레이션 15)으로 점수를 매겨 PR 본문에 표로 넣는다.

## 4.6단계: 심각도 게이트 + 자동 머지 판정

두 게이트는 재는 것이 다르다. Risk Score는 **바뀐 코드 자체**의 위험이고, 심각도는 **리뷰가 찾은 지적** 중 가장 센 등급이다. 하나가 다른 하나를 대신하지 못한다(작은 PR에도 버그가 있고, 지적 0건 PR도 마이그레이션을 건드린다).

- **심각도** = 이 브랜치의 가장 최근 리뷰(`sdd-review` 결과 표 또는 `code-reviewer` 보고)에서 남은(고치지 않은) 지적의 최고 등급. 🔴 크리티컬 / 🟡 경고 / 🟢 제안만 / 없음. **리뷰를 돌리지 않았으면 `미실행`** — 추측해서 채우지 않는다. 리뷰 결과는 파일로 남지 않는다(`review-{task}.json`은 BACKLOG) — **이 세션에서 본 리뷰가 없으면 `미실행`**. `확인 필요`(증명 못 한 지적, 등급 없음)는 `sdd-review` · `code-reviewer` 어느 쪽에서 나왔든 🟡로 센다 — 안 세면 심각도가 「없음」으로 잡혀 자동 머지 조건이 거짓으로 충족된다
- **자동 머지 조건 충족** = Risk Score **0~30** AND 심각도 **🟢 제안만 또는 없음**. 하나라도 아니면 `미충족`과 걸린 쪽을 적는다
- **세션 하나 작업**(검증 세션 없이 worktree 세션 하나로 한 작업)은 조건이 하나 더 붙는다: 새 맥락 `code-reviewer`를 1회 돌렸다(`sdd` 「③ REVIEW」). 안 돌렸으면 심각도는 `미실행`이라 미충족이다 — 만든 세션의 자기 리뷰(`sdd-review`)만으로는 충족되지 않는다
- 누가 머지하나: 지휘 아래 트랙 세션은 충족이고 PR CI가 통과하면 직접 머지한다(`conductor` §1 「트랙이 머지」, ADR-026 D2). 그 밖 세션은 판정만 적고 머지는 사람이 정한다
- `gh pr merge`는 `block-dangerous-bash`가 그 PR을 읽어 규칙 파일 변경 0 · Risk Score 30 이하 · CI 체크 전부 통과일 때만 확인 없이 통과시키고, 아니면 사람 확인(ask)으로 돌린다(ADR-026 D5). `--auto`는 쓰지 않는다 — 브랜치 보호가 없는 레포에서는 CI 전에 바로 병합된다

## 4.8단계: UI 변경 스크린샷

화면이 바뀐 PR은 리뷰어가 코드보다 화면을 먼저 봐야 판정이 빠르다. 그래서 스크린샷 칸을 본문에 만든다.

- **UI 변경 판정**: 바뀐 파일 중 `*.tsx` `*.jsx` `*.vue` `*.css` `*.scss` 또는 `components/` `pages/` `app/`(웹 앱) 아래 파일이 하나라도 있으면 UI 변경이다. 다만 테스트·스토리 파일(`*.test.*` `*.spec.*` `*.stories.*`)과 타입만 바뀐 경우는 빼고 센다
- **해당하면**: 본문에 `## 스크린샷` 절을 넣는다. 바뀐 화면마다 한 행을 두고 `전 | 후` 두 칸으로 나눈다. 화면은 번호가 아니라 이름으로 쓴다(예: `리뷰 목록 — 필터 열림`). 새 화면이면 `전` 칸에 `없음(신규)`을 적는다
- **이미지는 사람이 올린다**: `gh` CLI는 PR 본문에 이미지를 올리지 못한다. 칸에는 `<!-- 이미지 드래그 -->` 자리표시만 두고, 6단계 결과에 찍을 화면 목록을 낸다. 사용자는 GitHub 웹에서 PR 본문을 편집하고 이미지를 끌어다 넣는다
- **해당 안 하면**: `## 스크린샷` 절을 뺀다

## 4.95단계: 스키마 변경 이유

컬럼이 생기는 PR에서 작성자 말로 이유를 한 줄 받아 오래 남는 자리에 둔다 — 반년 뒤 "이건 왜 만들었지?"에 코드는 답하지 못한다.

- **판정**: 바뀐 파일 중 `db/migration/` 아래 파일·마이그레이션 `*.sql`·`schema.prisma`, 또는 diff에 `@Entity`·`@Table`·`@Column`이 들어간 파일이 있으면 해당. 없으면 이 단계와 PR 절을 뺀다
- **추출**: diff에서 새 테이블·추가 컬럼·바뀐 컬럼(타입·이름·삭제)만 뽑는다. 이 PR이 건드리지 않은 기존 컬럼은 소급하지 않는다
- **질문**: 컬럼마다 "왜 만들었고 누가 읽어요?"를 묻고 한 줄로 받는다(한 번에 목록으로 내고 줄마다 답). 🔴 **답은 작성자 말 그대로 — AI가 지어 채우지 않는다.** 모르면 `모름` → `⚠️ 미기록`. 채점·draft 전환은 없다(막지 않고 신호만)
- 같은 줄을 5단계 「스키마 변경 확인」 절에 넣는다

## 5단계: PR 본문 작성 후 생성

`${CLAUDE_PLUGIN_ROOT}/skills/pr-write/references/body-template.md`의 템플릿으로 본문을 작성하고 `gh pr create`로 PR을 생성한다. base 브랜치는 1단계의 `<base>`다.
레포에 `.github/PULL_REQUEST_TEMPLATE.md`가 있으면(harness-init이 CI와 함께 깐다) **그 섹션 구조를 채우고** 「전 → 후」 · 「바뀌지 않은 것」 두 칸과 Risk Score 표만 첫 섹션 아래에 이 순서로 추가한다 — 사람이 만든 PR과 모양이 같아야 리뷰어가 같은 자리를 본다.
「전 → 후」 · 「바뀌지 않은 것」은 고정 칸이다. 칸 제목 · 형식은 템플릿이 있는 레포에서도 body-template.md의 두 절을 그대로 쓴다. 지우지 않고, 쓸 것이 없으면 `해당 없음: <이유>` 한 줄을 둔다. PR마다 같은 자리에 상황 하나의 전과 후를 두어야 리뷰어가 바뀐 줄을 읽기 전에 판정할 수 있다.
본문 첫머리(템플릿이 있으면 첫 섹션)는 `sdd` ⑤ 마무리의 세 줄 요약을 그대로 쓴다(형식 정본은 그 절). `sdd` 밖에서 불렸으면 같은 세 줄을 지금 쓴다.
본문에 「모델이 검증한 것」(돌린 명령 · 결과)과 「사람이 볼 것」(`sdd-review` 「사람이 볼 것」 체크리스트 그대로, 항목마다 사람이 ✅ 또는 `건너뜀: <이유(선택)>`) 두 절을 나눠 둔다. `👤` 항목이 없으면 「사람이 볼 것」 절을 넣지 않는다. 건너뛰기는 막지 않는다 — 줄로 남기기만 한다.
draft는 사람이 원할 때만 `--draft`를 붙인다.

```bash
gh pr create \
  --base <base> \
  --title "<PR 제목>" \
  --assignee "<GitHub 로그인>" \
  --label "<유형 레이블>" \
  --label "<복잡도 레이블>" \
  --body "$(cat <<'EOF'
<본문>
EOF
)"
```

## 6단계: 결과 출력

PR 생성 후 URL과 함께 적용된 Assignee·Label을 사용자에게 알린다. UI 변경 PR이면 찍을 화면 목록(화면 이름 · 전/후)과 "PR 본문 편집 → 이미지 드래그" 한 줄을 같이 낸다. 스키마 변경 PR이면 "스키마 이유 n개 기록 · ⚠️ 미기록 n" 한 줄. 끝에 `쓴 원칙: <INDEX 이름|없음> · 바뀐 결정: <원칙을 읽고 달라진 판단 한 줄|없음>` 한 줄(PR 본문에는 넣지 않는다).
