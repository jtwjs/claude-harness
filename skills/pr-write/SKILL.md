작성 원칙: 사용자 영향 큰 변경을 두괄식 상단에, 리팩토링·테스트는 후순위, 단순 변수명·구조 변경은 제외. (상세 지침은 아래 "변경 사항" 템플릿 주석 참조 — 중복 서술 금지)

## 1단계: 변경 내용 수집

기준 브랜치: `.claude/harness.json`의 `git.baseBranch`(비었으면 `git symbolic-ref --short refs/remotes/origin/HEAD`에서 `origin/`을 뗀 값. 그것도 없으면 묻는다) = `<base>`.

```bash
git log <base>..HEAD --oneline          # 커밋 목록
git diff --name-only <base>...HEAD      # 변경 파일 목록
git diff <base>...HEAD                  # 전체 diff
git status --short                       # 미커밋 변경 확인
```

미커밋 변경이 있으면 PR 생성 전에 커밋 여부를 사용자에게 확인한다.

**현재 브랜치가 `<base>` 자신이면**(base 에 바로 커밋이 쌓인 경우) `<base>..HEAD` 가 비거나 틀린다 → `references/base-branch-rescue.md` 절차로 작업 브랜치로 옮긴 뒤(사용자 확인 필수) `origin/<base>` 기준으로 계속한다.

## 2단계: 원격 브랜치 푸시

현재 브랜치가 원격에 없거나 뒤처져 있으면 push한다:

```bash
git push -u origin HEAD
```

## 3단계: PR 제목 결정

제목은 커밋 메시지 형식과 같다 — `<type>: 요약`, 괄호 스코프는 `harness.json`의 `git.commitScope`가 `true`일 때만(**정본은 `commit` 스킬**). 예: `feat: 다건 이미지 DnD/paste 업로드 optimistic UI 적용`

## 4단계: Assignee·Label 결정

**Assignee**: `git config user.name` 또는 `gh api user --jq .login`으로 현재 작업자의 GitHub 로그인을 가져와 설정한다.

**Label**: diff와 커밋 내용을 바탕으로 아래 두 축에서 각각 1개씩 선택한다.

먼저 레포에 라벨이 있는지 확인한다 — 없는 라벨을 `--label` 로 넘기면 `gh pr create` 가 실패한다:

```bash
gh label list --limit 100 --json name --jq '.[].name' | grep -E '^(유형|복잡도): '
```

없으면 `--label` 을 빼고 PR 을 만든 뒤 «라벨 없음 — 만들까요?» 로 보고한다. 사용자 확인 없이 라벨을 만들지 않는다.

### 유형 레이블 (1개 선택)

| 레이블               | 선택 기준                                          |
| -------------------- | -------------------------------------------------- |
| `유형: 기능`         | 신규 기능·페이지·컴포넌트 추가 (`feat:` 커밋 포함) |
| `유형: 버그`         | 버그 수정 (`fix:` 커밋 위주)                       |
| `유형: 테스트`       | 테스트 코드만 변경                                 |
| `유형: 다큐멘테이션` | 문서·주석·README만 변경                            |

### 복잡도 레이블 (1개 선택)

| 레이블         | 선택 기준                                                          |
| -------------- | ------------------------------------------------------------------ |
| `복잡도: 쉬움` | 변경 파일 1~2개, diff 50줄 미만, 단순 수정                         |
| `복잡도: 보통` | 변경 파일 3~6개 또는 diff 50~200줄, 로직 변경 있음                 |
| `복잡도: 복잡` | 변경 파일 7개 이상 또는 diff 200줄 초과, 아키텍처·다수 레이어 변경 |

## 4.5단계: Risk Score 산출 (5축 0~100)

`references/risk-score.md`의 5축(보안 30 · 스코프 20 · Breaking 20 · 테스트 15 · 마이그레이션 15)으로 점수를 매겨 PR 본문에 표로 넣는다.

## 4.6단계: 심각도 게이트 + 자동 머지 판정 (dry-run)

두 게이트는 재는 것이 다르다. Risk Score는 **바뀐 코드 자체**의 위험이고, 심각도는 **리뷰가 찾은 지적** 중 가장 센 등급이다. 하나가 다른 하나를 대신하지 못한다(작은 PR에도 버그가 있고, 지적 0건 PR도 마이그레이션을 건드린다).

- **심각도** = 이 브랜치의 가장 최근 리뷰(`sdd-review` 결과 표 또는 `code-reviewer` 보고)에서 남은(고치지 않은) 지적의 최고 등급. 🔴 크리티컬 / 🟡 경고 / 🟢 제안만 / 없음. **리뷰를 돌리지 않았으면 `미실행`** — 추측해서 채우지 않는다. 리뷰 결과는 파일로 남지 않는다(`review-{task}.json`은 BACKLOG) — **이 세션에서 본 리뷰가 없으면 `미실행`**. `sdd-review`의 `확인필요`는 🟡로 센다
- **자동 머지 조건 충족** = Risk Score **0~30** AND 심각도 **🟢 제안만 또는 없음**. 하나라도 아니면 `미충족`과 걸린 쪽을 적는다
- 🔴 **지금은 dry-run이다.** 충족이어도 머지하지 않고 PR 본문에 판정만 적는다. 머지는 사람이 한다 — `gh pr merge`는 `block-dangerous-bash`가 매번 사람 확인(ask)으로 돌린다(0.18.1). 판정 정확도를 세는 법과 켜는 조건은 `BACKLOG.md` 「실제 자동 머지 켜기」 행(2026-10-13). 근거: 리뷰 등급의 정확도를 잰 적이 없고, 브랜치 보호가 없는 레포에서 `--auto`가 CI 전에 즉시 병합된 선례가 있다

## 4.8단계: UI 변경 스크린샷

화면이 바뀐 PR은 리뷰어가 코드보다 화면을 먼저 봐야 판정이 빠르다. 그래서 스크린샷 칸을 본문에 만든다.

- **UI 변경 판정**: 바뀐 파일 중 `*.tsx` `*.jsx` `*.vue` `*.css` `*.scss` 또는 `components/` `pages/` `app/`(웹 앱) 아래 파일이 하나라도 있으면 UI 변경이다(`docs/learning-level.md`의 `fe` 행과 같은 기준). 다만 테스트·스토리 파일(`*.test.*` `*.spec.*` `*.stories.*`)과 타입만 바뀐 경우는 빼고 센다
- **해당하면**: 본문에 `## 스크린샷` 절을 넣는다. 바뀐 화면마다 한 행을 두고 `전 | 후` 두 칸으로 나눈다. 화면은 번호가 아니라 이름으로 쓴다(예: `리뷰 목록 — 필터 열림`). 새 화면이면 `전` 칸에 `없음(신규)`을 적는다
- **이미지는 사람이 올린다**: `gh` CLI는 PR 본문에 이미지를 올리지 못한다. 칸에는 `<!-- 이미지 드래그 -->` 자리표시만 두고, 6단계 결과에 찍을 화면 목록을 낸다. 사용자는 GitHub 웹에서 PR 본문을 편집하고 이미지를 끌어다 넣는다. Test plan의 `(UI 변경 시) 스크린샷 첨부`는 체크하지 않은 채로 둔다
- **해당 안 하면**: `## 스크린샷` 절을 뺀다

## 4.9단계: 이해 게이트 — 분야별 블록 (PR 생성 직전)

리뷰를 요청하기 전에 작성자가 이 변경을 이해했는지 확인한다. 못 풀면 리뷰를 요청하지 않는다(draft). 검증은 에이전트에게 맡겨도 다음 작업에 쓸 이해는 맡길 수 없어서 둔다. **형식·분야 판정·레벨 파일의 정본은 `${CLAUDE_PLUGIN_ROOT}/docs/learning-level.md`** — 먼저 읽는다.

- **건너뜀**: 문서·설정만 바뀐 diff(`유형: 다큐멘테이션`). "이해 게이트 건너뜀 — 문서만" 한 줄 보고
- **레벨**: `~/.claude/learning-level.json`의 `levels`. 파일·값이 없으면 그 분야는 beginner
- **블록**: 바뀐 파일 경로로 분야(FE·BE·인프라)를 가르고 분야마다 그 레벨 형식의 블록 하나 + 도메인 블록 하나를 터미널에 낸다(예: `[FE·intermediate]` 객관식 3(큰 흐름 2 + 적용 1) · `[BE·beginner]` 기술 카드 2~3장 + 정답 공개 빈칸 1 · `[도메인·beginner]`). **beginner 블록은 채점·통과 판정이 없다** — 빈칸은 정답을 바로 보여 주는 되새김이다. 문항 있는 블록의 답은 한 줄로 받고 정답을 먼저 보여 주지 않는다. 전부 beginner면 설명을 낸 뒤 바로 5단계
- **채점 뒤 해설은 전 문항**: 맞힌 것 ✅ 왜 맞나 한 줄 · 틀린 것 ❌ 정답 + 왜 틀렸나 두 줄. 점수와 상관없이 낸다 — 찍어서 맞힌 것도 이해로 남기려고
- **문항 있는 블록이 전부 통과**(beginner 블록은 판정 밖) → 5단계 그대로
- **하나라도 미달** → 5단계를 `gh pr create --draft`로. 미달 블록만 다시 낸다. `explain-diff-html`(노션이면 `explain-diff-notion`) 한 줄 제안. 다시 풀어 통과하면 `gh pr ready <번호>`
- **기록**: 문항 있는 블록마다 `learning-level.json` `history`에 한 줄(`source: pr-quiz`, beginner 블록은 적지 않는다). beginner 도메인 블록 설명은 `_learn`에 `종류: 도메인 · 층: 회사|산업` 카드 한 장. 결과는 **PR 본문·커밋에 쓰지 않는다**. 틀린 블록은 `_learn/inbox.md`에 `종류: 막힌 질문 · 출처: PR 퀴즈` 카드(도메인 블록이면 `종류: 도메인 · 층: 회사|산업`)로 남긴다(없으면 건너뛰고 한 줄 보고)

## 4.95단계: 스키마 변경 이유 (이해 게이트 바로 뒤)

설계 때 만든 컬럼을 반년 뒤 "이건 왜 만들었지?"로 놓치고, 기능 논의에서 빠진 게 뒤늦게 발견된다. 그래서 컬럼이 생기는 PR에서 작성자 말로 이유를 한 줄 받아 오래 남는 자리에 둔다.

- **판정**: 바뀐 파일 중 `db/migration/` 아래 파일·마이그레이션 `*.sql`·`schema.prisma`, 또는 diff에 `@Entity`·`@Table`·`@Column`이 들어간 파일이 있으면 해당. 없으면 이 단계와 PR 절을 뺀다
- **추출**: diff에서 새 테이블·추가 컬럼·바뀐 컬럼(타입·이름·삭제)만 뽑는다. 이 PR이 건드리지 않은 기존 컬럼은 소급하지 않는다
- **질문**: 컬럼마다 "왜 만들었고 누가 읽어요?"를 묻고 한 줄로 받는다(한 번에 목록으로 내고 줄마다 답). 🔴 **답은 작성자 말 그대로 — AI가 지어 채우지 않는다.** 모르면 `모름` → `⚠️ 미기록`. 채점·draft 전환은 없다(막지 않고 신호만)
- **tables.md**: 레포에 `_brain/wiki/domain/tables.md`(`brain-walk` 테이블 표)가 있으면 해당 테이블 아래 「컬럼 메모」에 `` `컬럼` — 이유 · 읽는 곳 · YYYY-MM-DD `` 한 줄씩 추가한다(같은 컬럼 줄이 있으면 고친다, 삭제 컬럼은 줄을 지운다). 없으면 건너뛰고 "tables.md 없음 — `brain-walk` 제안" 한 줄 보고
- **커밋**: tables.md가 바뀌었으면 `docs(brain): 컬럼 이유 기록` 커밋 후 `git push`(2단계 push 뒤라서 한 번 더)
- 같은 줄을 5단계 「스키마 변경 확인」 절에 넣는다

## 5단계: PR 본문 작성 후 생성

아래 템플릿으로 본문을 작성하고 `gh pr create`로 PR을 생성한다. base 브랜치는 1단계의 `<base>`다.
레포에 `.github/PULL_REQUEST_TEMPLATE.md`가 있으면(harness-init이 CI와 함께 깐다) **그 섹션 구조를 채우고** Risk Score 표만 첫 섹션 아래에 추가한다 — 사람이 만든 PR과 모양이 같아야 리뷰어가 같은 자리를 본다.

```bash
gh pr create \
  --base <base> \
  --title "<PR 제목>" \
  --assignee "<GitHub 로그인>" \
  --label "<유형 레이블>" \
  --label "<복잡도 레이블>" \
  --body "$(cat <<'EOF'
<본문>
EOF
)"
```

### PR 본문 템플릿

기본 구조는 `Summary → Risk Score → 변경 유형 → 변경 사항 → 스크린샷(UI 변경일 때, 4.8단계) → 스키마 변경 확인(스키마 변경일 때, 4.95단계) → Test plan → 회고(SDD일 때) → 관련 이슈`. PR 성격에 따라 `변경 사항` 안에 원인/배경·동작 변화·머지 후 후속 작업 섹션을 자유롭게 추가한다. 큰 PR은 `### 1️⃣ … ### 2️⃣ …`로 분리.

```markdown

<!-- 무엇을 왜 변경했는지 1~3줄, 두괄식으로 -->

<!-- 5축 표 — references/risk-score.md 의 표를 그대로 -->
```

## 6단계: 결과 출력

PR 생성 후 URL과 함께 적용된 Assignee·Label·이해 게이트 결과(블록별 통과 · draft 여부 · 건너뜀)를 사용자에게 알린다. UI 변경 PR이면 찍을 화면 목록(화면 이름 · 전/후)과 "PR 본문 편집 → 이미지 드래그" 한 줄을 같이 낸다. 스키마 변경 PR이면 "스키마 이유 n개 기록 · ⚠️ 미기록 n · tables.md 반영|없음" 한 줄.
