# Explain

코드 하나가 **어떻게** 도는지와 **왜** 이렇게 됐는지를 한 이야기로 엮는다. 어떻게는 `how`(`${CLAUDE_PLUGIN_ROOT}/skills/how/SKILL.md`), 왜는 `why`(`${CLAUDE_PLUGIN_ROOT}/skills/why/SKILL.md`)의 절차로 읽고, 여기서는 둘을 묶는 일만 한다.

대상은 코드 변경(diff · 브랜치 · PR) 하나, 또는 지금 코드의 기능 하나다. 변경이면 바뀌기 전 흐름과 바뀐 흐름을 같이 본다.

## 읽기

1. **어떻게**: `how` 「어떻게 도나」대로 읽는다. 변경이면 바뀐 줄이 그 흐름의 어디에 끼는지까지.
2. **왜**: `why` 검증 모드의 코드 결정 줄대로 커밋 · PR · ADR에서 이유를 찾는다.

## 엮기

세 덩어리로 낸다.

- **배경**: 이 변경 · 기능이 기대는 지금 시스템. 주변 코드를 넓게 읽고 쓴다. 처음 보는 사람용 넓은 배경 → 바로 닿는 좁은 배경 순.
- **핵심 직관**: 세부가 아니라 핵심. 장난감 데이터로 구체 예를 들고 그림을 넉넉히 쓴다.
- **코드 순회**: 바뀐 코드 · 핵심 코드를 이해하기 쉬운 순서로 묶어 훑는다. 결정마다 어떻게(흐름의 어디)와 왜(기록의 이유)를 붙인다. 엮다가 `[추정]` 표시를 지우지 않는다 — 매끄러운 문장 속에서 추정이 사실처럼 굳는다.

깊이는 사람이 그 분야를 아는 만큼 맞춘다. 얼마나 아는지 모르면 넓은 배경을 앞에 두고 「아는 분야면 건너뛰세요」를 단다.

퀴즈 · 확인 질문은 내지 않는다. 사람이 되물으면 답한다.

## 대화가 기본, 「문서로」면 문서

말이 없으면 대화로 설명한다. 「문서로」 · 「HTML로」면 HTML, 「노션으로」 · 팀에 공유할 페이지면 노션. 내용은 같고 형식만 다르다.

문서 글: Martin Kleppmann처럼 명료하고 매끄럽게 잇는다(classic style). 그림 종류는 몇 개만 정해 되풀이한다(UI 변경이면 아주 단순한 UI, 데이터 흐름이면 예시 데이터가 흐르는 시스템 그림). 핵심 개념 · 정의 · 중요한 경계 사례는 callout으로 뺀다.

- **HTML**: CSS · JS가 든 자기완결 파일 하나. 절 제목과 목차가 있는 긴 한 장, 맨 위 탭 없음, 폰 폭 기본 반응형. 레포 밖에 오늘 날짜로 시작하는 이름으로 저장한다: `/tmp/YYYY-MM-DD-explanation-<slug>.html`. ASCII 그림 대신 단순 HTML 그림, 목록은 HTML 목록. 코드 블록은 `<pre>`, 직접 꾸민 div는 `white-space: pre-wrap` 필수 — 저장 전에 코드 블록마다 CSS에 `white-space: pre` 또는 `pre-wrap`이 있는지 훑는다.
- **노션**: 노션 MCP 도구로 새 페이지를 만들고 URL을 돌려준다.

## 학습 카드 재료 (`sdd` 마무리가 읽을 때)

대화 · 문서를 만들지 않는다. 이 작업의 diff에 「읽기」를 돌려, `${CLAUDE_PLUGIN_ROOT}/docs/learning-level.md` 기술 카드가 고르는 개념마다 어떻게(흐름 · `파일:줄`)와 왜(쓴 이유 · 안 쓰면 생기는 일)를 재료로 넘긴다. 카드 형식은 거기서 읽고 여기 다시 쓰지 않는다.
