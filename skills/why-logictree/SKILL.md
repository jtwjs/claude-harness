# /why-logictree — 로직트리 × So What-Why So 기획 작성

실제 기획서(제안서·PRD·문제정의서 등)를 쓸 때 쓰는 범용 스킬이다. 특정 프로젝트나 위키 구조에 종속되지 않는다 — 대화로 진행하고, 파일로 남길지는 사용자에게 물어서 정한다.

**절대 하지 않을 것**: 사용자가 준 적 없는 근거·수치·사실을 지어내지 않는다. 없으면 `⚠️ 근거 필요`로 표시하고 사용자에게 묻는다.

---

## 절차

### Step 1 — WHY 먼저

과제를 받으면 곧장 해결책(HOW)으로 뛰어들지 않는다. 먼저 묻는다:
- 이 과제를 왜 하는가? 겉으로 보이는 이유 말고, 진짜 이유·숨겨진 열망은?

사용자가 명확한 답을 갖고 있지 않으면 **WHY 트리**로 함께 파고든다 — "왜?"를 반복해서 표면적 이유 밑의 진짜 이유를 찾을 때까지. 사용자가 이미 WHY를 갖고 있으면 확인만 하고 Step 2로 넘어간다.

### Step 2 — 3질문으로 틀 잡기

1. **목표** — 원하는 미래는 무엇인가?
2. **진짜 문제** — 그 목표를 가로막는 진짜 문제는 무엇인가? (겉으로 보이는 증상과 구분)
3. **최적의 행동** — 실현 가능한 행동 중 무엇이 가장 결정적인가?

### Step 3 — 로직트리로 쪼개기 (Dividing)

문제나 목표를 실행 가능한 단위까지 잘게 쪼갠다. 손댈 수 있는 영역으로 나누고(Dividing), 의미 있는 단위로 다시 묶는다. 트리는 항상 **들여쓰기로 시각화**해서 보여준다.

- **WHY 트리** (원인 규명용): 해답이 나올 때까지 "왜?"를 반복한다.
  ```
  문제: OO이 안 된다
  └ 왜? 원인 A
    └ 왜? 더 구체적인 원인
      └ 왜? ... (실행 가능한 행동이 보일 때까지)
  ```
- **HOW 트리** (해결책 구체화용): 방안이 나올 때까지 "어떻게?"를 반복한다.
  ```
  목표: OO을 이룬다
  └ 어떻게? 방법 1
    └ 어떻게? 더 구체적인 방법
      └ 어떻게? ... (오늘 당장 할 수 있는 액션이 보일 때까지)
  ```
- 둘 중 하나만 필요할 수도, 둘 다 필요할 수도 있다 — 원인을 모르면 WHY 트리부터, 원인은 알고 방법이 안 잡히면 HOW 트리부터.

### Step 4 — So What / Why So로 검증

결론과 근거가 **양방향**으로 말이 되는지 검증한다.

- **Why So?** (결론 → 근거): "왜 그렇게 말할 수 있지?" — 이 결론을 뒷받침하는 구체적 근거가 있는가?
- **So What?** (근거 → 결론): "그래서 뭐가 되는데?" — 제시된 근거들로부터 이 결론이 타당하게 도출되는가?
- 한쪽만 있고 다른 쪽이 비면 짚어준다 — 근거 없는 결론(감으로 정한 해결책), 또는 결론 없는 근거 나열(그래서 뭘 어쩌라는 건지 불명확)
- **제목 가리기 테스트**: 기획서 제목·결론을 가리고 본문(근거·과정)만 읽었을 때 "무슨 문제를 풀려는지" 답이 나오는지 점검한다. 안 나오면 아직 논리에 구멍이 있다는 신호.

---

## 진행 방식

1. 사용자가 막연한 과제·아이디어를 던지면 Step 1(WHY)부터 시작. 이미 채워진 단계는 확인만 하고 건너뛴다.
2. 각 단계의 결과를 그때그때 명시적으로 구조화해서 보여준다 (트리는 반드시 시각화).
3. 마지막에 So What-Why So로 전체 논리를 점검하고, 구멍이 있으면 구체적으로 지적한다 (모호하게 "괜찮아 보입니다"로 넘어가지 않는다).
4. 사용자가 원하면 전체를 하나의 기획서 초안(목표 → 진짜 문제 → 최적 행동 → 근거)으로 정리해 제공한다.
5. 파일로 저장할지, 어디에 저장할지는 항상 사용자에게 먼저 묻는다 — 프로젝트마다 컨벤션이 다르므로 임의로 특정 파일·폴더에 쓰지 않는다.
