# /notion-writing: 공유 문서 작성

**한 줄**: 만드는 과정의 흔적을 전부 지우고, 결론과 그 근거만 남긴다.

**대전제**: 내 논리의 타당성보다 읽는 사람이 궁금한 정보가 먼저다. 문서의 목적은 설득이 아니라 상대가 판단할 근거를 주는 것이다.

**절대 하지 않을 것**: 근거·수치·사실을 지어내지 않는다. 없으면 `⚠️ 근거 필요`로 표시하고 묻는다. 작업 문서와 공유 문서를 한 파일로 겸하지 않는다. 파일로 저장할지, 어디에 저장할지는 사용자에게 먼저 묻는다.

## 절차

1. **독자와 결정 항목 확인**: 누가 읽고 무엇을 결정하는가. `결정·확인이 필요한 것`이 없으면 공유할 이유가 없다. 없으면 묻는다
2. **유형 판별**: 공유·제안 / 보고서 / 기획서 / PRD. 유형마다 통과 기준이 하나씩 있다(아래 표). 그 기준으로 끝까지 판정한다
3. **구성 결정**: 유형 표의 구성을 따른다. 작업 문서를 압축하는 경우 원본은 근거 원장으로 남기고 새 파일로 만든다
4. **표 중심으로 재구성**: 서술은 표 앞 1~2문장까지
5. **지우기 패스**: 해석 문장 → em dash → 볼드 → 메타 정보 순
6. **AI 티 점검**
7. **기계 검사**
8. **출력 헤더**를 붙여 제시하고 저장 여부를 묻는다

## 공통 규칙 (슬랙과 같음)

- 구조 4단: ①결론 ②근거·현황(숫자·사실) ③판단 근거(내 해석임을 드러냄) ④다음 액션
- 확신도 라벨(`[확인함]`·`[미확인·추정]`·`[확인 필요]`)은 공유본에서 문장 안에 풀어 쓴다. 라벨이 유일한 불확실성 신호였던 곳만 남긴다
- 톤: 음슴체. 상대에게 보내는 문의·요청 문서는 사실 서술만 음슴체, 요청 문장은 격식체. "부탁드림"은 무례하게 읽힌다
- em dash 0. 장식 이모지 0(심각도 `🔴`, 경고 `⚠️`만). 볼드는 문단당 1개
- 해석 문장을 지운다. 판별법: 앞 표나 문단을 지우면 이 문장도 성립하지 않으면 그건 해석이다. 연결은 독자가 한다
- 열린 질문은 제안값 + 확인 요청으로. 제안값은 문서에 이미 적은 논리에서만 끌어낸다

## 유형별 구성

| 유형 | 통과 기준 단 하나 | 구성 | 필수·주의 |
|---|---|---|---|
| 공유·제안(기본) | 독자가 결정 항목을 결정할 수 있는가 | `TL;DR(3줄)` → 1 왜 지금 이걸 해야 하나 → 2 무엇을 만드나 → 3 어떻게 만드나 → 4 무엇이 달라지나 → 5 결정·확인이 필요한 것 → 6 리스크와 한계 → 7 다음 액션 | 5절이 문서를 공유하는 이유. 나머지는 근거 |
| 보고서 | 의사결정에 도움이 되는가 | 결론 → 숫자 중심 사실 → 보고자 의견(해석임을 표시) → 다음 액션. 제안형이면 4질문(누구의 어떤 문제 / 문제의 크기·임팩트 / 왜 우리가·왜 지금 / 성공 측정) → 단계적 접근(가벼운 검증부터) → 우선순위 점수와 근거 | 모든 수치에 근거·출처. 미검증은 `확인 필요`로 남긴다 |
| 기획서 | 읽고 조직이 실제로 움직이는가 | Insight(문제·배경·현황 데이터) → Strategy(해결·구체화·실행 가능성) → Impact(일정·예산·KPI·리스크) | 예상 반론을 먼저 처리. 문제 먼저 / 해결책 먼저 중 독자에 맞춰 순서 선택. 절마다 독자 감정 목표(공감 → 신뢰 → 설득 → 확신 → 동의) |
| PRD | 문서만 보고 바로 구현을 시작할 수 있는가 | 배경·문제 → 목표·In/Out Scope → 기능 명세(유저스토리·BDD·예외) → 의존성·승인자 → 완료 기준·KPI | Out of Scope·예외·완료 기준은 PRD 필수라 "범위 밖은 적지 않는다"의 예외. 요구사항에 번호(FR-001) |

유형 불문: 필수 5요소(Why / Goal / What&How / Who / When&Impact) 중 하나라도 빠지면 "그래서 뭘 하라는 건가"가 돌아온다. 정성 표현("사용자 친화적")은 숫자로 바꾼다. 레퍼런스는 외부 사례보다 사내에서 이미 통과된 문서가 낫다.

## 형식

- H1을 넣지 않는다. 페이지 제목이 대신한다
- 표 중심. 다이어그램은 mermaid 1장. 코드 예시 0
- 사용자 언어로. 파일 경로·라이브러리·아키텍처 논증을 지운다. 문제 ID는 소수만
- 분량은 원문 250행 내외, 빈 줄 제외 170행 내외. 넘으면 잘라낼 후보를 제시하고 임의로 지우지 않는다
- 페이지 제목은 `유형__YYYYMMDD-NN 제목`(날짜 + 넘버링). "최종"을 붙이지 않는다

## 지우는 것

| 지울 것 | 처리 |
|---|---|
| 내가 덧붙인 해석 문장 | 삭제. 가장 중요하다 |
| 이번 범위 밖 항목 | "이번엔 안 함"이라고 적지도 않는다. 2차로 미룬 것만 `Out (2차)` 한 줄 |
| 문서에 대한 메타 정보(목차·머리말·버전 이력·부록) | 삭제. 독자는 문서에 대한 설명을 읽으러 온 게 아니다 |
| 작업 이력("○○ 정정" 블록) | 결과만 남긴다 |
| 인용문(대화 원문) | 삭제 |
| 확신도 라벨 | 문장 안에 풀어 쓴다 |
| 표의 부가 열(누가·ID·확신도) | 열을 늘리지 않는다 |
| 잴 수 없는 지표, 불확실한 수식·단위 | 측정 장치가 없으면 아예 쓰지 않는다 |

## AI 티

| 냄새 | 고치는 법 |
|---|---|
| `**현상.** / **영향.**` 볼드 라벨 뒤 마침표 | 순서는 두고 라벨을 걷어 문장으로 |
| 모든 절이 같은 3~4블록 | 절마다 필요한 만큼만 |
| 과한 볼드, 표 안 볼드 | 문단당 1개. 표 안에는 없음 |
| `> 참고:` 인용 블록 남용 | 본문에 흡수 |
| 같은 말 세 번(배경 문단 + 불릿 + 부연) | 한 문단으로 |
| 요약표와 우선순위표 중복 | 하나로 합치고 "회신은 표 순서로" 한 줄 |
| 절마다 "이 절에서는 ~를 다룹니다" 안내문 | 삭제 |
| 결론 뒤 "따라서 ~가 중요합니다" 훈계 | 삭제 |
| 항목을 억지로 3개씩 맞춘 병렬 | 있는 만큼만 |

## 기계 검사

em dash 0 · H1 0 · mermaid 1 이하 · wikilink 0 · 코드 경로 0 · 표의 열 수 일치 · 행 수. 결과를 한 줄로 사용자에게 보고한다(`em dash 0 · H1 0 · mermaid 1 · 170행`).

<!-- 아래부터 붙여넣기. 페이지 제목 제안: "유형__YYYYMMDD-NN 제목" -->
