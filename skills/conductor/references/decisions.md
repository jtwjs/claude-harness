# §1 결정 흐름 · §2 계약 변경 흐름 · §3 mock 관문

`conductor`가 결정 · 계약 변경을 이슈로 옮길 때 읽는다. `§N` · 「절 이름」은 `${CLAUDE_PLUGIN_ROOT}/skills/conductor/SKILL.md` 「상황 → 절」 표에서 파일을 찾는다.

## 1. 결정 흐름

**설계 결정은 지휘에서 사용자와 정하고, 문서 초안 · 코드 조사는 코드 옆에서 한다** (ADR-022 D6 — ADR-014를 좁힘). 자리마다 하는 일은 `${CLAUDE_PLUGIN_ROOT}/skills/conductor/references/seat.md` 「세 자리 역할」 표가 정본이다. 작업 중 새 설계 질문이 생기면 작업 세션은 사용자에게 직접 묻지 않고 지휘에 보고하고, 지휘가 이 흐름으로 정한다.

- **관문 둘** — 하나라도 열려 있으면 넘기지 않고 먼저 정한다
  1. 디스패치: 결정 이슈 「정할 것」 0 · 설계서 최종본일 때만 트랙 지시문을 보낸다(§5)
  2. 구현 시작(계획 쪼개기 포함): 구조 · 기술 결정 「정할 것」 0. 지금은 글로만 있고, 러너가 멈추는 장치는 러너 쪽 이슈 #83이 맡는다
- **설계서 흐름** — 지휘가 사용자와 설계서를 쓴다. 순서는 `${CLAUDE_PLUGIN_ROOT}/skills/sdd/references/design.md` 「설계서」 절이 정본이라 여기 다시 적지 않는다. 사용자와 주고받는 화면도 같은 절 「화면」을 따른다. 지휘는 auto 모드 그대로라 plan mode를 쓰지 않는다
- **코드 사실** — 결정에 코드 사실이 필요하면 작업 세션에 조사만 맡긴다. 작업 세션은 사실만 보고하고, 결정은 지휘가 사용자와 한다
- **결정 묶음 받기** — 트랙(나눔 모드는 검증 세션)이 레포 문서를 쓰다 결정이 나오면 파일:줄 근거를 붙인 결정 묶음으로 올린다 → 지휘가 설계서 「결정」 칸에 넣고 사용자에게 묻는다 → 사용자 답을 트랙에 회신한다. 지휘는 코드를 깊게 읽지 않고 묶음의 근거로 판단한다. 꼴은 `${CLAUDE_PLUGIN_ROOT}/skills/sdd/references/design.md` 「설계서」 절
- **사용자에게 가는 고르기 질문은 한 곳으로 보내고, 답은 그 턴에 결정 이슈 · ADR로 옮긴다** (ADR-022 D5 P6). 설계서가 걸린 질문은 설계서 화면으로 가고(`${CLAUDE_PLUGIN_ROOT}/skills/sdd/references/design.md` 「설계서」 절), 문서 없는 짧은 고르기만 한 곳으로 간다
  - 답을 받은 그 턴에 결정 이슈 · ADR(주체 · 이유)과 개인 기록으로 옮기고 「정할 것」에서 지운다. 결정 정본은 한 곳이 아니라 결정 이슈 · ADR이다. PR이 걸린 결정은 한 곳의 결정 내보내기로 PR에도 남긴다
  - 보낼 때마다 지휘 탭에도 「Inbox에 질문 n개」 한 줄을 남긴다. 알림이 사용자에게 뜨는지 아직 모른다
  - 한 곳에는 지휘만 보낸다. 트랙은 지휘에 묻는다. 권한 확인 창(머지 등)은 지휘 탭에 남는다
  - 지금 한 곳은 `plannotator` Inbox다(질문 블록 · 막지 않음 · `export-decisions`로 스레드 · PR을 지정해 결정 내보내기). 고르기 전용 도구(다시 설계 중)가 오면 이 줄만 되돌린다
- 지휘는 이슈 번호로 회신한다. 트랙은 번호를 받기 전까지 그 결정을 확정된 것으로 쓰지 않는다
- **판정 거르기** (#29) — 사용자에게 묻기 전에 지휘 자리 문서 · 그 레포 규칙 · ADR부터 훑어 거른다. 사용자에게 가는 질문을 줄이되, 사용자가 정할 것은 빼앗지 않는다

  | 판정 | 언제 | 어떻게 |
  |---|---|---|
  | 지휘가 정함 | 정본(지휘 자리 문서 · 레포 규칙 · ADR)에 답이 있고 되돌리기 쉽다 | 결정 이슈에 「AI가 정함 + 근거 경로」로 남긴다. 사용자는 보기만 하고, 아니면 반려한다 |
  | 사용자에게 올림 | 새 취향 · 트레이드오프 · 되돌리기 어려움(삭제 · 공개 계약) · 보안 경계 확대 · 외부 발송 | 맥락을 다 채운 세부 판정만, 추천 + 이유를 붙여 한 곳으로 보낸다(위 줄) |

  애매하면 사용자에게 올린다

- **설계서는 지휘, 레포 세 문서는 검증 세션** (ADR-022 D2 — ADR-019 E4 갱신) — 지휘는 설계서를 지휘 자리 폴더에 쓰고 결정 이슈 「설계서」 칸에 경로를 적는다. 다른 레포 worktree에 직접 쓰지 않는다. 검증 세션이 설계서 최종본으로 PRD · ARCHITECTURE · ADR을 쓰고 의도 되비추기 한 줄을 지휘에 보낸다. 설계서를 고쳐야 하면 지휘가 사용자와 설계서를 고치고, 검증 세션이 다시 반영한다. 공개 레포면 PRD에 사람 이름 · 개인 문서 문구 · 개인 기록 원문을 넣지 않고 일반화한다
- 기능 키워드 표 · API 계약 초안을 결정 이슈에 두는 이유(ADR-019 E9 · E10): FE · BE 검증 세션이 같은 원문을 PRD로 옮겨 가야 용어와 계약이 갈리지 않는다

```markdown
결정: <한 줄>

## 정할 것
<아직 안 정한 것 한 줄씩. 0이 돼야 디스패치한다(관문 둘)>

## 근거
<쿼리 결과·문서 링크·실측. 없으면 §3 관문>

## 대안
<버린 안과 버린 이유>

## 설계서
<설계서 최종본 경로(지휘 자리 폴더). 트랙에 맡길 기능이 아니면 "해당 없음". 수용 조건은 검증 세션이 설계서로 PRD에 쓴다>

## 기능 키워드
| 용어 | 이 기능에서의 뜻 |
|---|---|

## API 계약 초안
<FE · BE 기능일 때: 엔드포인트 · 필드 · 에러. 아니면 "해당 없음">

## 전파 체크리스트
- [ ] PRD — <경로 또는 "해당 없음">
- [ ] BRIEF(트랙 복사본) — <경로 또는 "해당 없음">
- [ ] ERD — <경로 또는 "해당 없음">
- [ ] 영향 step 파일 — <phases/... 또는 "해당 없음">
- [ ] 픽스처 — <경로 또는 "해당 없음">

영향 트랙: track:<a> track:<b>
```

1. 라벨: `conductor` `decision` + 영향 트랙 라벨
2. 체크리스트 한 줄 = 담당 트랙의 `follow-up` 이슈 하나(`conductor` `follow-up` `track:<담당>`). 본문 첫 줄은 `Decision: #<결정 번호>`
3. 후속 이슈를 결정 이슈의 하위로 건다(`issues.py sub`, §4). 후속끼리 순서가 있으면 `issues.py block`
4. 후속이 **전부 닫히면** ADR로 옮긴다. 🔴 **ADR 번호는 여기서만 발급한다**:
   ```bash
   git -C <레포> fetch -q origin && git -C <레포> grep -h -o 'ADR-[0-9]\{3\}' origin/<기준 브랜치> -- 'docs/*/ADR.md' | sort -u | tail -1
   ```
   최대 번호 + 1. 로컬 작업 트리가 아니라 **원격 기준 브랜치**를 본다(로컬은 늦다). 열린 PR에 든 ADR 번호도 `gh pr list -R <owner>/<repo> --search "ADR-" --state open`으로 한 번 본다
5. ADR을 담는 PR은 해당 트랙이 올린다. 지휘는 번호와 본문 초안만 넘긴다
6. 결정 이슈에 ADR 링크를 코멘트로 남기고 닫는다

막힌 질문 번호도 같은 이유로 지휘가 발급한다.

## 2. 계약 변경 흐름

`contract-change` 이슈(`conductor` `contract-change` + 영향 트랙). 본문: 바뀌는 엔드포인트·스키마 · 이유 · 호환 여부.

| 변경 | 바로 발행할 후속 |
|---|---|
| required 필드 추가 · enum 값 변경 · 타입 변경 | 소비 트랙 `follow-up`: 픽스처·생성 타입 재생성·화면 분기 |
| **계약에 안 드러나는 의미 변경**(기준·주기·단위·집계 범위) | 소비 트랙 `follow-up`: 화면 문구·툴팁·도움말 |
| 엔드포인트 삭제·개명 | 소비 트랙 `follow-up` + 제공 트랙에 "소비 쪽 닫힌 뒤 삭제" `issues.py block` |

스키마가 같아도 의미가 바뀌면 생성 타입 diff가 0이라 CI가 못 잡는다. 그래서 두 번째 줄이 있다.

**나눔 모드 — 계약 먼저** (ADR-019 E9). FE · BE 층마다 검증 · 구현 세션을 둔 기능이면:

1. 첫 배치: 검증 BE의 첫 step은 결정 이슈 「API 계약 초안」으로 만든 계약 PR(스펙 파일)이고, 먼저 병합한다(`tracks.md` §5). 검증 FE의 첫 step은 병합된 스펙으로 MSW 핸들러 · 타입을 만든다. 그 뒤 두 층 구현은 동시에 간다
2. 변경: 누구든 계약을 바꿔야 하면 지휘에 보고한다 → 지휘가 `contract-change` 이슈를 연다 → 검증 BE의 스펙 PR이 먼저 병합된다 → 검증 FE가 따라간다(위 표의 후속). 트랙끼리 직접 메시지로 계약을 주고받지 않는다(§8)
3. 끝까지 확인: 검증 FE가 머지 전에 MSW를 끄고 기준 브랜치에 들어온 실제 BE로 한 번 돌린다. BE가 계약을 먼저 굳혀 앞서 들어오므로 나중에 PR을 내는 쪽이 늘 FE다

## 3. mock 관문

enum 값 · 주기 · 테이블 구조를 **계약으로 굳히기 전에** 운영 실측 근거(쿼리 결과·원천 문서 링크)를 이슈 본문 「근거」에 적게 한다.

- 근거가 없으면 `blocked` 라벨 + 본문 첫 줄 `Blocked: 운영 근거 없음 — <무엇을 세야 하나>`
- PRD 표기 · 회의 기록 · mock 값은 근거가 아니다. 운영에 그 값이 있는지 센 결과가 근거다
