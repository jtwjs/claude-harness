`sdd-run` 산출 diff를 **설계문서 대비 체크리스트**로 빠르게 판정한다. 심층·다축 리뷰(성능·구조·보안 감사)는 **`code-reviewer` 에이전트**에 위임한다.

## 1. 기준 로드 (이 파일들만)

- 루트 `CLAUDE.md`
- 설계문서 폴더는 **`phases/{task}/index.json`의 `docs`** 에서 읽는다(`sdd-plan`이 채움). `task`를 모르면 묻고, `docs/` 아래를 뒤져 추측하지 않는다.
- `{docs}/ARCHITECTURE.md`(구조·레이어) · `ADR.md`(기술 결정) · `PRD.md`(수용 조건 — §3 「수용 조건 대조」 축이 늘 쓴다)
- `${CLAUDE_PLUGIN_ROOT}/agents/code-reviewer.md`의 「증명 규칙」 절 — 의도 되비추기 · 지적의 근거 · 「확인 필요」 강등 · 확신 단계는 그 절을 따른다. 그 파일의 다른 절(4축 · 등급 재조정)은 `code-reviewer` 몫이다.

## 2. 변경 수집

- `git diff --name-only <base>...HEAD`(또는 `git diff HEAD`)로 변경 파일 파악 — `<base>`는 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/base-branch.sh"` 출력(exit 2면 사람에게 묻는다) → 필요한 파일 맥락 확인. diff가 비면 범위를 한 번 확인.
- **회차**(#10) — `phases/{task}/index.json`의 `reviews`(없으면 빈 목록) 길이 + 1이 이번 회차다. 2회차부터는 **직전 회차의 `head` 이후 diff(`git diff <head>..HEAD`)만** 대조한다. 단 「빌드·테스트」 축의 `verify`는 늘 전체로 돌린다. 이전 회차의 `issues`에 있는 지적은 다시 내지 않는다.

## 3. 체크리스트 대조

| 축            | 확인                                                                                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 아키텍처 준수 | `{docs}/ARCHITECTURE.md`의 계층 배치·의존 방향과 일치. `.claude/rules/`가 금지한 경계 위반 없음                                                              |
| 기술스택·ADR  | `ADR.md` 결정과 일치. **미승인 새 의존성 없음**(추가됐다면 어느 ADR이 허락했는지 대라). ADR을 인용할 땐 번호 옆에 괄호로 한 줄 — `ADR-003(설정 스키마를 blocks 패키지에)` |
| 수용 조건 대조 | PRD 수용 조건의 `AC-N` 번호마다 테스트 위치 표(번호 · 테스트 `파일:줄` · 통과 여부)를 낸다. 맡는 쪽이 이 세션 몫인데 테스트가 없는 번호는 🟡. 번호가 없는 옛 PRD는 `harness.json.tdd.include` 범위의 변경 파일에 짝 테스트가 있는지만 보고 「번호 없음」 한 줄. 어느 쪽이든 **동작 기준**으로 단언(구현 디테일 아님). 대상 판정은 `.claude/rules/testing.md` §0 |
| CRITICAL 규칙 | `CLAUDE.md`의 🔴 CRITICAL 각 항목을 **그대로 대조**. 자동 생성물 미수정. hook 우회(`--no-verify`)는 `.claude/settings.json` `permissions.deny`(템플릿에 깔림)가 막는다 — 리뷰는 deny 줄이 깔렸는지만 본다 |
| 빌드·테스트   | `.claude/harness.json`의 `verify`를 **실제 실행**해 통과 확인. 앱별이면 root마다 그 폴더에서 돌리고 결과를 root 이름으로 적는다. 비어 있는 키는 그 사실을 보고한다          |
| 실제 동작     | **verify 통과는 동작 증거가 아니다** — 목·스텁·MSW로 바꾼 경계는 계약 위반을 못 잡는다. UI·API·외부 연동을 바꿨으면 앱을 띄워(`run` 스킬·브라우저·실 백엔드) 바뀐 경로를 **한 번 실제로** 지나가 본다. 못 했으면 `확인 필요 — 미실행: 이유`로 보고하고 통과로 적지 않는다. 디자인 트랙이면 시각 대조는 `design-reconcile`이 하고 여기는 동작만 본다 |

## 4. 출력 형식

1. **의도 · 리뷰 범위** — 되비춘 의도 한 줄, diff 범위·파일 수(1~2줄).
2. **결과 표** — 각 축: `통과 / 위반 / 확인 필요` + 근거(파일:라인 · 돌린 명령 · 출력 · 확신 단계).
   - 🔴 크리티컬(빌드·타입 붕괴·CRITICAL 위반·명백 버그) / 🟡 경고(규칙·경계·테스트 누락) / 🟢 제안.
3. **수정 제안** — 항목별 `파일:라인 — 문제 — 수정 방향`. 실제 수정은 하지 않는다. 고치는 경로는 `sdd` REVIEW 절과 같다 — 수정 step을 하나 더 만들어 `sdd-run`으로, 작은 수정만 `feature-builder`.
   - **종류로 묶는다** — 한 줄을 고치라고 하지 않고, 같은 종류(같은 패턴·같은 누락)의 위치를 grep으로 전부 찾아 한 항목에 모은다. 작성자가 한 번에 고치게.
   - **원래 있던 문제(pre-existing)는 따로** — 지적한 줄이 이번 diff(`<base>...HEAD`) 밖이거나 `git blame`상 이 작업 전 커밋이면 `원래 있던 문제` 절에 목록으로만 둔다. 수정 step을 만들지 않고, 후속 이슈로 할지는 사람이 정한다.
4. **회차 기록** — `index.json`의 `reviews`에 `{"at": <시각>, "head": <지금 HEAD>, "issues": [<이 작업 지적 종류 한 줄씩>]}`을 append한다. 위반이 남았고 이번이 **3회차**면 수정 제안 대신 "3회차가 끝났다 — 접근 방식 자체를 다시 볼까요?"를 사람에게 묻는다(`sdd` REVIEW 절 ④).
5. **사람이 볼 것** — PRD 수용 조건 중 `👤` 표시가 붙은 번호만 체크리스트(`- [ ] AC-N — <기준 한 구절>`)로 낸다. 표시가 없으면 이 칸을 생략한다.
6. **`code-reviewer` 판정** — 「위임」의 조건대로 불렀으면 그 보고를, 안 불렀으면 `code-reviewer 건너뜀: <이유>` 한 줄.
7. **다음 단계** — 통과 시 REFLECT로. 순서와 커밋 메시지 규칙은 여기 다시 적지 않는다 — **순서는 `sdd` SKILL.md의 ⑤ 마무리 절, 메시지 형식(`git.commitScope`)은 `commit` 스킬이 정본**이다. `--no-verify` 금지만 여기서도 한 번 더.

## 위임

- **`code-reviewer`를 부르는 조건**(나눔 모드 검증 세션) — 아래 셋 중 하나면 Agent 도구로 부른다. 안 부르면 출력에 `code-reviewer 건너뜀: <이유>`.
  1. 변경 파일이 `.claude/harness.json` `review.gatePaths`(계약 · 마이그레이션 · 권한 경로 glob)에 닿는다. 목록이 비었거나 키가 없으면 이 조건은 세션이 판단하고 이유를 한 줄 적는다
  2. `pr-write` Risk Score가 자동 머지 기준을 넘는다(기준 값은 `pr-write` 4.6단계가 정본)
  3. 이 리뷰에 「확인 필요」가 남았다
- 세션 하나 모드는 이 조건을 보지 않는다 — `sdd` 「③ REVIEW」 절대로 이 리뷰 뒤 새 맥락 `code-reviewer`를 늘 한 번 부른다(같은 세션 자기 리뷰를 막는다).
- 부를 때 fork하지 않는다 — 만든 쪽 맥락을 물려받으면 자기 리뷰가 된다(탐색 같은 보조 작업은 해도 된다). 성능/구조 건강성/보안을 깊게 봐야 할 때는 조건 밖이어도 부를 수 있다.
- 원인 불명 회귀 → `root-cause-debugger`.
- 이 스킬은 판정만 한다(코드 수정 없음).
