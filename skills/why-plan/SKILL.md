정리되지 않은 요청을 **공유된 이해**까지 끌고 간다. 왜를 먼저 파고(로직트리), 설계 트리를 가지 하나씩 내려가며(인터뷰) 결정 사이의 의존을 푼다.

> 2026-10-11 `grilling`(인터뷰 → PRD)과 `why-logictree`(WHY·로직트리 → 기획서)를 합쳤다. 둘 다 WHY → 3질문 → So What/Why So 를 돌았고, 다른 것은 「한 번에 한 질문 + 갈래 + PRD」와 「트리 시각화」뿐이었다.

## 규칙

- **한 번에 한 질문.** 답을 받고 다음으로 간다.
- 질문마다 **추천 답**을 같이 낸다. 추천은 과제의 목적(WHY)에 비춰 왜 그것인지까지.
  - **예외 — 설계 결정**(데이터 모델·API 계약·에러 처리·경계 선택)은 **사람의 생각과 이유를 먼저 받고 추천은 그 뒤에** 낸다. 내 이유에 한 번 반박한다. 추천이 먼저 보이면 그대로 고르게 되고(실측: 한 인터뷰 5문항 5/5 추천 수용), 사람은 나중에 그 설계를 설명하지 못한다. 범위·저장 경로처럼 사소한 결정은 추천 먼저.
- **질문은 짧게.** 첫 줄에 정할 것 한 문장, 선택지는 2~3개를 쉬운 말과 "고르면 생기는 일" 한 줄로. 새 용어는 처음 나올 때 괄호로 정의한다.
- **선택지마다 앞으로의 영향을 적는다** — 무엇이 굳고, 무엇이 비싸지고, 나중에 무엇을 정해야 하나. 영향은 코드·문서로 확인한 사실로만, 확인 못 한 것은 «미확인».
- **쉬운 말로 묻는다.** 사람이 «무슨 말이야» 로 되물으면 질문이 실패한 것이다 — 같은 질문을 더 쉽게 다시 쓴다.
- **사실은 찾고, 결정은 묻는다.** 코드·문서로 확인할 수 있는 것은 직접 찾는다.
- **지어내지 않는다.** 사람이 준 적 없는 근거·수치는 `⚠️ 근거 필요`로 남기고 묻는다.
- 공유된 이해에 도달했다고 **사람이 확인하기 전에는 실행하지 않는다.**

## 순서

0. **날것 그대로 받는다.** 구조 없는 요청이 정상 입력이다. 받은 것을 정리해 주지 말고 **"들은 것 / 빈칸"으로만 되비추고** What if 두 개로 넓힌다. 이 원문은 PRD 머리에 그대로 남긴다 — 인터뷰가 AI의 구조로 시작하면 이후 결정도 AI의 것이 된다.
1. **WHY 먼저.** "왜 하는가 — 겉 이유 말고 진짜 이유는?" 답이 얕으면 **WHY 트리**로 함께 판다. 이미 답이 있으면 확인만 한다.
   ```
   문제: OO이 안 된다
   └ 왜? 원인 A
     └ 왜? 더 구체적인 원인 (실행 가능한 행동이 보일 때까지)
   ```
2. **세 질문으로 틀을 잡는다.** ① 목표 — 원하는 미래는? ② 진짜 문제 — 목표를 막는 것은?(증상과 구분) ③ 최적 행동 — 실현 가능한 것 중 가장 결정적인 것은?
3. **참고 자료를 묻는다 — 반드시 묻고, 답은 선택이다.** "참고할 슬랙 스레드·노션·문서·URL·이전 결정이 있나요?" 받으면 읽고 요지를 되비춘다. "없음"이면 그대로 진행한다. 슬랙 원문·사람 이름은 산출물에 옮기지 않는다(링크 + 요지 한 줄).
4. **갈래를 내려간다.** 범위 · 수용 조건(관찰 가능한 동작으로) · 경계(하지 않을 것) · 데이터·상태 · 실패 경로 · 기존 코드와의 접점. 앞 답이 뒤 질문을 바꾸면 순서를 바꾼다.
   - **옛 시스템을 이어받는 과제면 요구와 방법을 가른다.** 요구(무엇이 되어야 하나 · 안전·보안 규칙)는 승계하고, 방법(화면 배치·입력 방식·중복 컨트롤)은 다시 묻는다.
5. **안 잡히면 로직트리로 쪼갠다.** 원인을 모르면 WHY 트리, 원인은 아는데 방법이 안 잡히면 **HOW 트리**. 트리는 항상 들여쓰기로 보여준다.
   ```
   목표: OO을 이룬다
   └ 어떻게? 방법 1
     └ 어떻게? 더 구체적인 방법 (오늘 할 수 있는 액션이 보일 때까지)
   ```
6. **양방향으로 검증한다.** Why So(결론 → 근거가 있나) · So What(근거 → 이 결론이 나오나). 한쪽이 비면 짚는다 — 감으로 정한 해결책, 결론 없는 근거 나열. **제목 가리기 테스트**: 결론을 가리고 근거만 읽어도 무슨 문제를 푸는지 나오는가.

## 끝 — 산출물 세 갈래

사람이 "됐다"고 하면 나눠 남긴다. **저장 경로는 제안하고 확인받는다.**

1. **스펙**
   - 코드 작업 → `docs/{feature-YYYY-MM-DD}/PRD.md` (항목은 아래 「설계문서 3장」).
   - 문서가 목적(기획서·제안서·문제정의서) → 목표 → 진짜 문제 → 최적 행동 → 근거 순의 초안. 위치는 묻는다.
2. **`_brain` 맥락** (레포에 `_brain/`이 있을 때 — 팀 위키·인수인계용, 커밋된다)
   - `_brain/wiki/decisions/<기능>.md`: 목적·이유·배경 3줄 · 버린 대안(+이유) · 참고 자료(링크 + 요지 한 줄) · PRD 경로. 형식은 `_brain/CLAUDE.md` 노드 템플릿.
   - 이 기능이 끝나도 남는 이 제품·회사의 규칙은 `_brain/wiki/domain/`(또는 용어면 `glossary/`).
   - 구현 PR과 **같은 PR**에 태운다. 원문·사람 이름·개인 vault 경로는 적지 않는다.
3. **`_learn` 카드** (개인 학습, 커밋 안 됨) — 인터뷰 중 사람이 몰랐던 **기술·직무** 개념은 `_learn/inbox.md` 머리 형식으로 한 장씩.
   - 가르는 기준 한 줄: **회사를 옮겨도 쓸모 있나** → 예면 `_learn`, 아니면 `_brain`. 둘 다 걸치면 쪼갠다(`_learn`엔 개념, `_brain`엔 이 프로젝트의 쓰임과 이유).

step 승인 직전에 불렸으면(계획에 `⚠️`·TBD가 3개 이상) PRD를 새로 쓰지 않고, 푼 결정을 해당 step 파일에 반영한다.

## 설계문서 3장 (`docs/{feature-YYYY-MM-DD}/`) — DESIGN 단계 산출물의 정의

이 스킬이 PRD를 만들고, ARCHITECTURE·ADR은 PRD가 확정된 뒤 같은 폴더에 쓴다. `harness`(PLAN)·`harness-run`·`sdd-review`가 이 세 파일을 읽는다.

**PRD.md**: 무엇을(한 문장) · 왜 — 진짜 문제와 성공지표(**비포 값**을 같이 적는다. 아직 못 쟀으면 `미측정: 방법 / 기한` — 비포가 없으면 애프터가 나와도 개선을 증명할 수 없다) · 참고 자료(링크 + 요지) · 사용자 시나리오 · 범위(포함 / 하지 않을 것) · **수용 조건 체크리스트**(관찰 가능한 동작으로 — `test-writer`가 케이스를 뽑는 입력이다) · 남은 `⚠️`.
**ARCHITECTURE.md**: 개요 · 계층 배치와 각 층의 책임 · 데이터 흐름 · 경계·의존 방향 · 상태 관리 규약 · 테스트 전략. **구체 스택 이름은 그 프로젝트의 것을 쓴다.**
**ADR.md**: `ADR-00N` 블록 반복 — 상태 · 맥락 · 결정 · **결정 주체**(사람 / AI 추천 수용) · 대안(+버린 이유) · 결과(트레이드오프). 결정 주체는 회의에서 "내가 고른 것"과 "추천을 받은 것"을 가르는 칸이다 — 후자가 많으면 그 결정들이 리허설 대상이다.
**다른 ADR을 가리킬 때 번호만 쓰지 않는다** — 처음 나올 때 괄호로 무엇을 정했는지 한 줄 붙인다(`ADR-003(설정 스키마를 blocks 패키지에)`). 문장 끝에 근거로 묶어 다는 자리(`(ADR-003·ADR-007)`)는 예외.
