git 변경사항을 분석해서 Changeset 파일을 자동으로 작성해줘.

## 0단계: 대상인지 확인

`.claude/harness.json`의 `release.tool`을 읽는다. `"changesets"`가 아니면(없거나 `null`) **여기서 멈추고 한 줄 보고한다** — `release.tool 이 changesets 가 아니라 changeset 을 건너뜀`. description이 "스스로 skip"이라고 약속하는데 본문에 이 단계가 없었다(2026-10-08).

## 1단계: 변경 내용 수집

아래를 순서대로 실행해서 변경 내용을 파악한다:

```bash
git log <base>..HEAD --oneline         # <base> = harness.json git.baseBranch, 비었으면 origin/HEAD (pr-write 와 같은 규칙. main 하드코딩 금지)
git diff HEAD --stat                   # 변경 파일 목록과 규모
git diff HEAD                          # 실제 diff
# 모노레포면 워크스페이스별로: git diff HEAD -- <workspace-dir>/
```

diff가 없으면 `git diff --cached --stat` 로 staged 변경도 확인한다.
변경된 주요 파일은 Read 도구로 내용을 직접 읽어 컨텍스트를 보강한다.

## 2단계: Changeset 필요 여부 판단

| 변경 내용                         | 필요 여부 | bump       |
| --------------------------------- | --------- | ---------- |
| 새 기능·페이지·주요 컴포넌트 추가 | ✅        | `minor`    |
| 버그 수정·UI 개선·성능·리팩토링   | ✅        | `patch`    |
| API 구조 변경·브레이킹 체인지     | ✅        | `major`    |
| 테스트·문서·CI·스타일만 변경      | ❌        | 생성 안 함 |

**불필요한 경우**: 이유를 설명하고 종료한다.

## 3단계: slug 추론

브랜치명을 사용하지 않는다.  
**커밋 메시지와 변경된 파일·코드 내용을 분석**해 변경을 가장 잘 표현하는 2~3단어 영문 레이블을 만든다.

규칙:

- 형식: `{동사}-{도메인}` 또는 `{동사}-{도메인}-{상세}` (kebab-case, 소문자)
- 동사 후보: `add`, `fix`, `update`, `remove`, `improve`, `refactor`
- 도메인은 변경된 feature/entity 이름 기반 (`article`, `tag`, `publish`, `channel`, `image` 등)
- 2단어가 충분히 명확하면 3단어로 늘리지 않는다

예시:
| 변경 내용 | slug |
|---|---|
| 기사 복제 기능 추가 | `add-article-copy` |
| 태그 10개 초과 에러 수정 | `fix-tag-limit` |
| 발행 설정 유효성 개선 | `improve-publish-validation` |
| 채널 변경 시 카테고리 초기화 | `fix-channel-category-reset` |
| 기사 목록 페이지네이션 추가 | `add-article-pagination` |

## 4단계: 파일 생성

**경로**: `.changeset/{slug}.md`

**형식**:

```
---
"<package-name>": {patch|minor|major}
---

{한국어 요약 1~3문장}
```

### 대상 패키지 정책

- 대상 패키지는 **워크스페이스 설정에서 읽는다**(`pnpm-workspace.yaml`·`package.json`의 `workspaces` 등). 이름을 지어내지 않는다.
- 사용자 영향이 있는 `feat/fix/refactor` 변경이면 changeset을 생성한다. 변경이 걸친 패키지마다 각각.
- `.changeset/config.json`의 `ignore` 패키지는 대상에서 제외한다.
- 단일 패키지 레포면 그 패키지 하나만 쓴다.

**요약 작성 기준**:

- 커밋 메시지 복붙 금지 — diff 기반으로 새로 서술
- "무엇이 바뀌었는지" + "사용자·팀원에게 어떤 의미인지" 포함
- 좋은 예: **무엇이 생겼고 그걸로 뭘 할 수 있는지**가 한 문장에 다 있는 것 — "목록에서 항목을 복제하는 기능 추가. 기존 내용을 복사해 새 항목을 바로 시작할 수 있습니다."
- 나쁜 예: "복제 기능" (너무 짧고 맥락 없음)
- **patch 요약은 맨 앞에 분류 마커를 단다** — 개선이면 `개선:`, 버그 수정이면 `수정:`. 릴리즈 노트를 이 마커로 분류할 수 있다(마커 없으면 수정으로 본다). `minor`·`major`는 마커 불필요(항상 "새 기능").

### 이 요약은 그대로 사용자에게 노출된다 — 사용자 언어로 쓸 것 (필수)

changeset 요약은 `CHANGELOG.md`를 거쳐 **릴리즈 노트에 문구 변경 없이 실린다.** 중간에 다시 써 주는 사람은 없다 — **여기 쓴 표현이 곧 사용자가 읽는 문장**이다.

**쓰지 말 것** — 내부 어휘가 릴리즈 노트로 새는 것은 실제로 일어난다:

| 부류 | 어떤 것이 여기 해당하나 | 대신 |
| --- | --- | --- |
| **내부 enum·코드값** | 권한·상태를 코드가 부르는 이름 그대로 | 사람이 부르는 이름 |
| **내부 식별자·번호** | id·번호로 가리키는 권한/설정 | 그 권한·설정의 이름 |
| **API·필드명** | 엔드포인트·응답 필드 | 언급하지 않는다 — 사용자가 겪는 **증상·결과**만 |
| **URL 경로** | 화면을 경로로 지칭 | **화면 이름** |
| **UI 구현 용어** | 모달·드로어·스켈레톤 등 구현자의 말 | 사용자가 쓰는 말(창·목록·안내) |
| **구현 수치·스펙** | px·캐시 시간·z-index | 눈에 보이는 결과("크기를 맞췄습니다") |

> 판정 한 줄: **"이 단어를 우리 서비스 사용자가 쓰나?"** 아니면 바꾼다.

**예** — 같은 변경, 다른 표기:

- ❌ `수정: 인스타 수집처 수정 화면이 channel-edit로 조회해 프리필이 안 되던 문제 수정. channel-get으로 교정.`
- ✅ `수정: 인스타 수집 설정에서 수집처 수정 화면을 열 때 기존 정보가 채워지지 않던 문제를 수정했습니다. 이제 계정 유형·계정·표시 이름·카테고리·페르소나 값을 정상적으로 불러옵니다.`

**첫 문장이 굵은 제목이 된다** — L1의 `splitLeadAndRest`가 첫 문장(`…다.`/`…요.`)을 `- **제목**`으로, 나머지를 `— 설명`으로 가른다. 첫 문장은 **한 줄로 짧게** 끊고 상세는 두 번째 문장부터 쓴다. 첫 문장에 부연을 다 넣으면 제목이 통째로 굵어져 읽기 어렵다.

## 5단계: 결과 출력

```
파일: .changeset/{slug}.md
bump: patch | minor | major
slug 근거: {커밋/diff에서 어떤 내용을 읽고 추론했는지 한 줄}
이유: {bump 선택 근거 한 줄}
```

생성 후 커밋하지 않는다. 개발자가 내용을 확인한 뒤 `/commit` 커맨드로 함께 커밋하도록 안내한다.
