# 트랙 운영

> 병렬 트랙(worktree 세션 2개 이상)으로 진행하는 레포의 절차. 트랙 표는 `harness-init` ⑧이 인터뷰로 채운다.
> 지휘 세션 하나는 `conductor` 스킬로 돈다(결정·계약 변경·예외 판정·ADR 번호 발급).
> 원형은 트랙 3개 병렬 레포의 절차 문서(2026-09-29~10-08 실측)다. 도메인을 빼고 절차만 남겼다.

## 트랙 표

작업(PR) 하나 = `feature/<트랙>-<주제>` 브랜치 하나 = worktree 하나. 작업은 **자기 트랙 소유 경로만** 고친다. 트랙은 폴더가 아니라 소유 규칙이다.

| 트랙 | 소유 경로 | 라벨 |
|---|---|---|
| <!-- harness-init ⑧ --> | | `track:<이름>` |

| 공유 구역 | 경로 | 바꾸는 길 |
|---|---|---|
| 계약 | <!-- 예: API 스키마 파일 --> | 제공 트랙 PR + 소비 트랙 후속(§5) |
| 공유 설정 | <!-- 예: CI · 루트 설정 --> | 공유 구역 PR(§4) |

- phase 이름은 `<트랙>-<과제>`. 한 phase를 두 트랙이 돌리면 `index.json`이 충돌한다
- 마이그레이션은 그 테이블을 쓰는 트랙 PR에 같이 넣는다. 버전은 타임스탬프라 트랙끼리 겹치지 않는다
- ADR 번호는 지휘가 발급한다. 트랙 세션은 매기지 않는다(`conductor` §1)

## 1. worktree 만들고 지우기

`<기준 브랜치>` 최신에서 만들고 PR이 병합되면 지운다. 서브에이전트의 `isolation` 옵션에 기대지 않고 직접 만든다 — 옵션만 믿었다가 부모 트리의 브랜치가 바뀐 적이 있다.

```bash
git fetch origin
git worktree add ../<레포>-<트랙>-<주제> -b feature/<트랙>-<주제> origin/<기준 브랜치>
git worktree list
```

- worktree는 커밋하지 않은 변경을 가져가지 않는다. 필요한 것은 기준 브랜치에 먼저 병합해 둔다
- PR이 병합되면 `git worktree remove ../<레포>-<트랙>-<주제>` 후 로컬 브랜치를 지운다. 폴더만 지우면 git에 기록이 남는다(`git worktree prune`)
- 새 worktree에는 설치물(`node_modules` 등)이 없다. 의존성 설치부터 돌린다. 패키지 저장소·빌드 캐시는 전역이라 짧다

## 2. 로컬 자원 충돌

| 자원 | 문제 | 대응 |
|---|---|---|
| 포트 | 두 worktree가 같은 포트로 뜨면 부딪힌다. 로컬 E2E가 `reuseExistingServer`로 **다른 worktree의 서버를 재사용**할 수 있다 | 동시에 띄우는 작업은 포트를 옮긴다(환경변수 · `--port`) |
| 컨테이너 | compose는 폴더 이름 기준 프로젝트로 뜬다 | worktree마다 `COMPOSE_PROJECT_NAME`을 다르게 둔다(⚠️ 원형 레포에서도 미검증) |
| CPU · Docker | 트랙마다 Stop 훅이 verify 전체를 돈다. 동시에 끝나면 몰린다 | 무거운 검증은 트랙 사이에 시차를 둔다 |

## 3. 트랙 세션 · 서브에이전트에 넘길 것

새 세션은 이 대화를 모른다. `.claude/references/track-brief.md`를 채워 넘긴다(지휘가 채운다). 최소한:

1. 트랙 이름과 소유 경로(위 표의 그 행)
2. 돌릴 phase 경로 `phases/<트랙>-<과제>/`
3. 계약 경로(소비 트랙은 생성 타입만 쓴다)
4. 완료 조건: `harness.json` `verify` 중 자기 쪽 명령의 출력
5. "소유 경로 밖을 고쳐야 하면 멈추고 보고하라"

## 4. 공유 구역 PR

1. 공유 구역 변경만 담은 브랜치(`chore/<주제>`)를 기준 브랜치에서 딴다
2. 작게 올려 **먼저** 병합한다
3. 각 트랙은 `git merge origin/<기준 브랜치>`로 받아 간다

## 5. 계약 먼저 PR

제공 트랙이 계약을 바꾸면:

1. 계약 변경(스키마 + 재생성한 계약 파일)을 담은 PR을 먼저 병합한다. 구현은 뒤 PR로 와도 된다
2. 소비 트랙은 기준 브랜치를 받아 생성 타입을 재생성한다
3. required 필드 · enum 변경이면 소비 쪽 픽스처 · 테스트 데이터가 같이 깨진다. 같은 PR에 픽스처 한 줄을 넣을지는 지휘가 판정한다(`conductor` §6)
4. 스키마가 같고 의미만 바뀌면(기준 · 주기 · 단위) 생성 타입 diff가 0이다. 소비 쪽 문구 후속을 지휘가 발행한다(`conductor` §2)

## 6. 합칠 때 (Fan-in) 확인

1. 제공 PR에 재생성한 계약 파일이 들어 있다(계약 테스트 통과)
2. 소비 트랙에서 기준 브랜치를 받고 타입을 재생성한다 — 빠뜨리면 CI 계약 단계가 생성물 불일치로 실패한다
3. 소비 쪽 typecheck — 깨지는 곳이 곧 계약이 어긋난 곳이다
4. `harness.json` `verify` 전체(앱별이면 앱마다)
5. 전체 브랜치 리뷰 1회(`sdd-review`, 필요하면 `code-reviewer`)

## 7. 쌓인 PR 병합 함정 (2026-09-29 실측)

- `gh pr merge --delete-branch`는 다음 PR의 **대상 브랜치**를 지워 그 PR을 닫는다. 먼저 `gh pr edit <다음> --base <기준 브랜치>`로 대상을 옮기고 병합한다
- 스쿼시 뒤 다음 브랜치는 `git rebase --onto origin/<기준 브랜치> <이전 브랜치 끝> <다음 브랜치>` 후 `git push --force-with-lease`. 하네스 훅은 보호 브랜치 이름이 든 강제 push만 막으므로 feature 브랜치 이름만 적어 실행한다
- `git merge -X ours`는 쓰지 않는다. 충돌 hunk를 전부 내 쪽으로 정해 기준 브랜치에 먼저 들어간 변경을 조용히 버리고, CI는 초록으로 끝난다
